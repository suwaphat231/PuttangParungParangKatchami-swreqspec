**Software Requirements Specification**

**ระบบ LAB BOY**

# 1 Introduction

## 1.1 วัตถุประสงค์

เอกสารนี้ระบุความต้องการของระบบ LAB BOY ให้ทีมพัฒนา ผู้ตรวจ และผู้สอนใช้ร่วมกัน โดยรวบรวมจาก spec.md ของ 22 Use Case ซึ่งเป็นแหล่งความจริงเดียวของโปรเจกต์ (Spec-Driven Development) ผู้อ่านเป้าหมาย: ทีมพัฒนา ผู้ตรวจสอบความต้องการ และผู้สอน

## 1.2 ขอบเขตของระบบ

ระบบ LAB BOY รองรับกระบวนการตั้งแต่ประกาศรับสมัคร การสมัคร การตรวจสอบสถานะและเอกสาร การคัดเลือก การจัดตารางปฏิบัติงาน การประเมินและส่งผล การติดตามการจ่ายเงิน ไปจนถึงการจัดการผู้ใช้ สิทธิ์ และการแจ้งเตือน ครอบคลุม 22 Use Case ดังนี้

**นอกขอบเขตของระบบ** เช่น การดำเนินการจ่ายเงินในระบบการเงินเอง การคืนเงิน/ยกเลิกการชำระเงิน การเริ่ม/หยุด/รีสตาร์ทบริการโดยตรง การออกแบบนโยบาย IAM ระดับองค์กร การกำหนดหรือแก้ไขปฏิทินการศึกษา การส่งข้อความจริงต่อผู้ใช้ (UC-20) และการอนุมัติกลางก่อนเผยแพร่ประกาศ (UC-15)

# 2 Overall Description

## 2.1 ภาพรวมระบบและความสัมพันธ์กับระบบอื่น (System Context)

ระบบ LAB BOY เชื่อมต่อกับระบบภายนอก 6 ระบบตามที่ spec ระบุ ลูกศรแสดงทิศทางข้อมูลหลัก

ความสัมพันธ์ระหว่าง UC ที่ spec ระบุ: UC-09 เรียก UC-19 ตรวจวัน-เวลา · UC-08 และ UC-14 ส่งผลแจ้งผู้สมัครผ่านการแจ้งเตือน (UC-20/UC-22) · UC-16 ใช้ข้อมูลที่ UC-21 อัปเดต · UC-17 และ UC-18 กำกับบทบาทและสิทธิ์ของ UC-04

## 2.3 สภาพแวดล้อมการทำงาน

- เว็บแอปพลิเคชัน ใช้ผ่านเว็บเบราว์เซอร์บนคอมพิวเตอร์และมือถือ

- Frontend แยกตามบทบาท เรียก Backend ผ่าน API และใช้ฐานข้อมูลกลางร่วมกัน

## 2.4 ข้อจำกัด (Constraints)

รวบรวมจากหัวข้อ Constraints ของแต่ละ spec ไม่มี CON-TECH ข้อใดของระบบ Lab Boy

### UC-01 สมัครเป็น Lab Boy

- ต้องเข้าสู่ระบบก่อนสมัคร

- ต้องมีประกาศรับสมัครที่อยู่ในช่วงเวลาเปิดรับ

- ข้อมูลที่จำเป็นจากบัญชีผู้ใช้ต้องครบก่อนยืนยัน

- หากสมัครสำเร็จต้องไม่สร้างใบสมัครซ้ำสำหรับประกาศเดียวกัน

- ใช้ข้อมูลจากบัญชีผู้ใช้โดยไม่ต้องแนบเอกสาร

- หากจำนวนผู้สมัครเต็ม ให้รับคำขอตามลำดับเวลาที่ยืนยันสำเร็จ

### UC-02 ดูประกาศรับสมัคร

- ประกาศที่หมดเขตไม่ควรแสดงเป็นรายการที่สมัครได้

- ข้อมูลประกาศต้องมาจากข้อมูลที่เจ้าหน้าที่/อาจารย์เผยแพร่

### UC-03 ดูสถานะการสมัคร

- ผู้ใช้ดูได้เฉพาะใบสมัครของตนเอง

- สถานะต้องอ้างอิงจากข้อมูลล่าสุดในระบบ

- ผู้ใช้ต้องเข้าสู่ระบบก่อนดูสถานะ

- รายการใบสมัครเรียงจากรายการที่อัปเดตล่าสุดก่อน และกรองตามประกาศได้

### UC-04 เข้าสู่ระบบ

- ต้องมีบัญชีที่ได้รับอนุญาต

- ต้องไม่เปิดเผยรหัสผ่านหรือข้อมูลยืนยันตัวตน

- ต้องยืนยันตัวตนผ่าน SSO ของสถาบัน

- อนุญาตเฉพาะรหัสนักศึกษา/บุคลากรหรืออีเมลมหาวิทยาลัย


### UC-05 ตรวจสอบสถานะนักศึกษา

- ต้องใช้ข้อมูลจากระบบทะเบียนที่เชื่อถือได้

- ไม่ควรเก็บข้อมูลส่วนบุคคลเกินความจำเป็น

### UC-06 เปิดรับสมัคร

- ผู้เปิดรับสมัครต้องมีสิทธิ์ในรายวิชาหรือกิจกรรม

- วันเปิดต้องไม่มากกว่าวันปิด

### UC-07 ดูรายชื่อผู้สมัคร

- ระบบต้องแสดงข้อมูลเฉพาะในรอบ/รายวิชาที่อาจารย์มีสิทธิ์

- ข้อมูลส่วนบุคคลต้องถูกจำกัดตามบทบาทและนโยบายการเข้าถึงข้อมูล

- หากอาจารย์ไม่มีสิทธิ์ในรอบใด ระบบต้องปฏิเสธการเข้าถึงการดูข้อมูลของรอบนั้น

### UC-08 คัดเลือกผู้สมัคร

- คัดเลือกได้เฉพาะอาจารย์เจ้าของวิชาในรอบรับสมัครนั้น

- การคัดเลือกจำกัดเฉพาะผู้สมัครที่อยู่ระหว่างการพิจารณา

- อาจารย์สามารถยืนยันผลได้โดยไม่ต้องมีการอนุมัติซ้ำ และไม่จำกัดจำนวนผู้ผ่านตามจำนวนที่รับ

### UC-09 จัดทำตารางปฏิบัติงาน

- ห้ามจัดตารางซ้อนกันสำหรับ Lab Boy คนเดียวกัน โดยถือว่าซ้อนกันเมื่อช่วงเวลาใหม่ทับกับช่วงเวลาเดิมแม้เพียงบางส่วน

- ต้องไม่เกินโควตาของแต่ละช่วงเวลา

- อนุญาตให้แก้ไขตารางได้ก่อนถึงเวลาเริ่มปฏิบัติงานเท่านั้น หลังถึงเวลาเริ่มปฏิบัติงานแล้วห้ามแก้ไข

### UC-10 ตรวจสอบเอกสารและอนุมัติ

- เข้าถึงเอกสารได้ตามสิทธิ์

- เมื่อส่งกลับหรือไม่อนุมัติ ต้องระบุเหตุผลก่อนบันทึกผลการตรวจ

- เอกสารที่ผู้สมัครส่งใหม่หรือแก้ไขแล้ว ต้องมีการตรวจใหม่ตามกระบวนการที่กำหนด

- ประวัติการตรวจสอบและเวอร์ชันเอกสารต้องถูกบันทึกเพื่อใช้ตรวจสอบย้อนหลัง

### UC-11 ประเมินการปฏิบัติงาน

- ต้องมีเกณฑ์การประเมินที่กำหนด

- ต้องกรอกข้อมูลที่บังคับครบก่อนยืนยัน

### UC-12 ส่งผลการปฏิบัติงาน

- ต้องประเมินครบก่อนส่ง

- เมื่อส่งแล้วต้องไม่แก้ไขโดยไม่มีสิทธิ์

### UC-13 ตรวจสอบสถานะผู้ปฏิบัติงาน

- เจ้าหน้าที่ภาควิชาเห็นข้อมูล Lab Boy เฉพาะรายวิชาที่สังกัดภาควิชาตนเอง

- อาจารย์ผู้สอนเห็นเฉพาะ Lab Boy ในรายวิชาที่ตนเองรับผิดชอบ

- ผู้ดูแลระบบเห็นข้อมูลทุกภาควิชาและสามารถสลับภาควิชาที่ต้องการดู

- สถานะต้องมาจากข้อมูลล่าสุด และแสดง timestamp หลักที่ถูกอัปเดต

### UC-14 ตรวจสอบเอกสารนักศึกษา

- รายการเอกสารบังคับต้องถูกกำหนดจากประกาศรับสมัครแต่ละฉบับเป็นแหล่งข้อมูลหลัก (Single Source of Truth)

- การเข้าถึงเอกสารและใบสมัครต้องถูกควบคุมตามสิทธิ์และบทบาทของผู้ใช้งาน (RBAC)

- เมื่อผลการตรวจสอบไม่ผ่านหรือส่งกลับเพื่อแก้ไข ต้องระบุเหตุผลหรือข้อบกพร่องที่ชัดเจน

- ก่อนยืนยันส่งกลับ ระบบต้องบันทึกรายการเอกสารที่มีปัญหาและเหตุผลที่ต้องแก้ไขให้ครบถ้วนก่อน จึงจะสามารถกดยืนยันได้

- ระบบต้องบันทึกประวัติการตรวจสอบแบบแก้ไขไม่ได้ (Immutable Audit Log)

- การแจ้งกลับไปยังผู้สมัครต้องใช้ระบบแจ้งเตือนภายในแอปเป็นช่องทางหลัก และอีเมลเป็นช่องทางเสริม

### UC-15 จัดทำประกาศรับสมัคร

- ฟิลด์ข้อมูลบังคับต้องครบถ้วนก่อนเปลี่ยนสถานะเป็น Published

- ประกาศแบบ Draft สามารถบันทึกไว้ก่อนเผยแพร่โดยไม่บังคับให้กรอกทุกฟิลด์

- ผู้จัดทำต้องมีสิทธิ์ของภาควิชา และผู้ดูแลระบบ (Admin) มีสิทธิ์เปลี่ยนสถานะ Draft → Published ได้ทันที

- สถานะประกาศต้องเป็นไปตาม lifecycle: Draft → Published → Expired / Archived

- ประวัติการจัดทำและการเปลี่ยนสถานะต้องถูกบันทึกแบบ append-only

### UC-16 ติดตามและตรวจสอบการจ่ายเงิน

- ข้อมูลการเงินเข้าถึงได้เฉพาะผู้มีสิทธิ์ตามบทบาทและสิทธิ์ของผู้ใช้งาน

- HR และ Manager/Executive ดูข้อมูลการจ่ายเงินได้แบบ Read-only; Student และผู้ปฏิบัติงานทั่วไปไม่มีสิทธิ์เข้าถึงหน้าติดตามการจ่ายเงิน

- หน้าติดตามและตรวจสอบเป็นแบบ Read-only ไม่อนุญาตให้แก้ไขข้อมูลต้นทางหรือเปลี่ยนสถานะการจ่ายเงินผ่านหน้าจอนี้

- ระบบการเงินเป็นแหล่งข้อมูลสถานะการจ่ายเงินที่ถูกต้องและเป็นแหล่งข้อมูลหลัก

- อนุญาตให้ใช้ Mock Finance Data สำหรับพัฒนาและทดสอบ Backend และ Prototype UI โดยต้องระบุชัดว่าเป็นข้อมูลสมมติ แยกจากข้อมูลจริง และห้ามอ้างว่าเชื่อมต่อระบบการเงินจริงแล้ว

- ขอบเขตการพัฒนาประกอบด้วย Backend API/Business Logic และ Prototype UI แยกงานกัน; UI ใช้ Mock Data ภายใน Frontend เท่านั้น ไม่เรียก API หรือเชื่อม Database

- Prototype UI แสดงยอดเงินและสถานะในรูปแบบเดียวกันตาม Q-01, มีสรุปจำนวนตามสถานะ, ค้นหา/กรองรายการ และแสดงรายละเอียด; เป็น Read-only และไม่เพิ่มความสามารถแก้ไขยอดหรือสถานะ

- Prototype UI ไม่ใช่ขอบเขตบังคับสิทธิ์หรือ Audit Log; การบังคับสิทธิ์และบันทึก Audit Log ยังคงเป็นความรับผิดชอบของ Backend ตาม FR-PAY-04/05 และ AC-PAY-04/05

- ข้อมูลใน Prototype UI ต้องแสดงข้อความชัดเจนว่าเป็นข้อมูลสมมติสำหรับสาธิต ไม่ใช่ข้อมูลการเงินจริง

- รายการที่ยังไม่จ่ายหรือผิดปกติต้องถูกทำเครื่องหมายชัดเจนเพื่อให้เจ้าหน้าที่ดำเนินการต่อ

- สำหรับการสาธิต UC-16 ให้ตรวจ Bearer Token จาก server-side mapping ใน \`PAYMENT_DEMO_AUTH_TOKENS\` รูปแบบ JSON ที่จับคู่ token กับ \`user_id\` และ role; เปิดใช้ได้เฉพาะ \`APP_ENV=local\` หรือ \`APP_ENV=test\` และค่าเริ่มต้นต้องปิดแบบ production

- บันทึกการอนุญาต/ปฏิเสธของ UC-16 ลงตาราง Audit Log แยก โดยเก็บผู้ใช้ เวลา resource/item และผลการตรวจสิทธิ์; ห้ามบันทึก bearer token และห้ามรับ role จาก request

- API สำหรับ UC-16 ใช้ \`GET /payments\` ค้นหา/กรอง, \`GET /payments/{payment_id}\` อ่านสถานะล่าสุดรายรายการ และ \`GET /payments/follow-up\` อ่านรายการที่ต้องติดตาม; ทุก endpoint เป็น Read-only

### UC-17 จัดการระบบ

- เฉพาะผู้ดูแลระบบที่ได้รับสิทธิ์เท่านั้นที่สามารถเข้าถึงเมนูและฟังก์ชันจัดการระบบ

- ระดับสิทธิ์หลักประกอบด้วย นักศึกษา, อาจารย์, เจ้าหน้าที่, และ System Owner โดย นักศึกษาเป็นผู้ใช้งานทั่วไป, อาจารย์มีสิทธิ์อนุมัติการเปลี่ยนแปลงสำคัญตามนโยบายระบบ, เจ้าหน้าที่ดู/จัดการค่าตั้งค่าและผู้ใช้ที่ได้รับมอบหมาย, และ System Owner ดูแลเกี่ยวกับระบบเป็นหลักและดู/แก้ไขค่าระดับระบบ

- ระบบต้องป้องกันการบันทึกข้อมูลที่ไม่ครบถ้วน ไม่ถูกต้อง หรือซ้ำ

- การเปลี่ยนแปลงที่กระทบความปลอดภัยหรือการทำงานหลักต้องมีการยืนยันและบันทึก audit log ก่อนให้มีผลบังคับใช้

- การตั้งค่าบางรายการที่สำคัญต้องมีการอนุมัติจาก อาจารย์ หรือผู้มีสิทธิ์เพิ่มเติมตามนโยบายของระบบ

- ระบบต้องแสดงสถานะอัปเดตล่าสุดของบริการและบันทึกเวลาเมื่อสถานะเปลี่ยนแปลง

- ผู้ใช้งานไม่สามารถอนุมัติการเปลี่ยนแปลงที่ตนเองส่งคำขอได้

### UC-18 อนุมัติสิทธิ์การเข้าใช้งาน

- สิทธิ์หรือบทบาทที่อนุมัติต้องสอดคล้องกับ role matrix และนโยบาย IAM ที่กำหนด

- ระบบต้องปฏิเสธคำขอที่มีบทบาทหรือสิทธิ์อยู่นอกรายการที่อนุญาต

- การปฏิเสธคำขอต้องมีเหตุผลและไม่สามารถบันทึกเป็นเว้นว่างได้

- การอนุมัติหรือปฏิเสธต้องระบุผู้อนุมัติและเวลาของการพิจารณา

### UC-19 ตรวจสอบวันและเวลาปฏิบัติงาน

- ปฏิทินการศึกษาที่ใช้ในการตรวจสอบต้องเป็นข้อมูลที่ระบบยอมรับและมีความสดใหม่ตามข้อกำหนด

- หากระบบไม่สามารถเรียกข้อมูลปฏิทินหรือข้อมูลไม่ครบถ้วน ไม่ว่าจะเป็นข้อมูลล้าสมัย หรือข้อมูลไม่พร้อมใช้งาน ต้องไม่ถือว่าผ่าน

- การตรวจสอบต้องพิจารณาว่าช่วงเวลาที่ขอมีการทับซ้อนกับช่วงเวลาที่ห้ามปฏิบัติงานหรือไม่

- ผลลัพธ์ของการตรวจสอบต้องมีสถานะเป็น Pass หรือ Fail และมีเหตุผลที่ชัดเจน

### UC-20 ส่งคำขอแจ้งเตือน

- ธุรกรรมหลักต้องไม่รอผลการส่งคำขอแจ้งเตือน

- คำขอแจ้งเตือนต้องมีข้อมูลที่จำเป็นต่อการประมวลผลเท่านั้น และต้องไม่เปิดเผยข้อมูลที่เกินสิทธิ์

- ระบบต้องสามารถรองรับการส่งซ้ำเมื่อมีปัญหาการเชื่อมต่อหรือระบบปลายทางไม่พร้อม

### UC-21 ตรวจสอบการจ่ายเงิน

- ระบบการเงินเป็นแหล่งข้อมูลที่เชื่อถือได้สำหรับสถานะการจ่ายเงิน

- reference ต้องเป็นคีย์ที่ใช้เชื่อมรายการภายใน LAB BOY กับรายการในระบบการเงิน

- ระบบต้องปฏิเสธการอัปเดตเมื่อ reference หรือข้อมูลสถานะไม่ตรงกับรายการที่มีอยู่

- การอัปเดตสถานะต้องเป็น idempotent และไม่สร้างรายการซ้ำ

- การเชื่อมต่อกับระบบการเงินต้องใช้การส่งข้อมูลที่เข้ารหัส

### UC-22 แจ้งเตือนผู้ใช้งาน

- ส่งเฉพาะผู้รับที่มีสิทธิ์และมีข้อมูลช่องทาง

- ข้อความต้องไม่เปิดเผยข้อมูลส่วนบุคคลเกินจำเป็น

## 2.5 ข้อสมมติและสิ่งที่ต้องพึ่งพา

### 2.5.1 ข้อสมมติ (ASM ตาม spec)

### UC-01 สมัครเป็น Lab Boy

- ASM-01 คุณสมบัติผู้สมัครถูกกำหนดไว้ในประกาศรับสมัคร

- ASM-02 ใช้เขตเวลา Asia/Bangkok

- ASM-03 ข้อมูลที่ใช้สมัครดึงจากบัญชีผู้ใช้ และไม่มีเอกสารแนบ

- ASM-04 การถอนใบสมัครทำได้จนถึงเวลาที่อาจารย์ปิดรับสมัคร

- ASM-05 อาจารย์เป็นผู้ดำเนินการใบสมัครสถานะ \`รอตรวจสอบ\`

- ASM-06 การจัดลำดับผู้สมัครใช้เวลาที่ระบบยืนยันคำขอในเขตเวลา Asia/Bangkok

### UC-02 ดูประกาศรับสมัคร

- ASM-01 ข้อมูลประกาศมีผู้รับผิดชอบตรวจสอบก่อนเผยแพร่

### UC-03 ดูสถานะการสมัคร

- ASM-01 มีชุดสถานะมาตรฐานที่กำหนดไว้

- ASM-02 ผู้ใช้ต้องเข้าสู่ระบบก่อนเข้าดูสถานะ

- ASM-03 สถานะ \`ผ่าน\` และ \`ไม่ผ่าน\` เปลี่ยนโดยอาจารย์เท่านั้น

- ASM-04 ใช้เขตเวลา Asia/Bangkok สำหรับวันเวลาที่อัปเดตล่าสุด

- ASM-05 ระบบโหลดข้อมูลล่าสุดเมื่อเปิดหน้า

### UC-04 เข้าสู่ระบบ

- ASM-01 ระบบยืนยันตัวตน/บัญชีผู้ใช้มีข้อมูลบทบาท

- ASM-02 ใช้ SSO ของสถาบันเป็นผู้ให้บริการยืนยันตัวตน

- ASM-03 ไม่ใช้ MFA

- ASM-04 session ใช้ idle timeout 120 นาที

- ASM-05 logout ยกเลิกเฉพาะ session ของอุปกรณ์ปัจจุบัน

- ASM-06 บทบาทที่รองรับคือ นักศึกษา อาจารย์ เจ้าหน้าที่ และผู้ดูแลระบบ

- ASM-07 เก็บ audit login อย่างน้อย 1 ปี

### UC-05 ตรวจสอบสถานะนักศึกษา

- ASM-01 มี API/ช่องทางเชื่อมต่อระบบทะเบียน

### UC-06 เปิดรับสมัคร

- ASM-01 รายวิชาและผู้รับผิดชอบมีอยู่ในระบบ

### UC-07 ดูรายชื่อผู้สมัคร

- ASM-01 ข้อมูลผู้สมัครผ่านการบันทึกจาก UC-01

### UC-08 คัดเลือกผู้สมัคร

- ASM-01 จำนวนที่รับกำหนดในประกาศ

- ASM-02 อาจารย์เป็นผู้พิจารณาและเลือกผู้สมัครด้วยตนเอง

- ASM-03 การแก้ไขผลคัดเลือกไม่ต้องบันทึกเป็นประวัติการเปลี่ยนแปลง

### UC-09 จัดทำตารางปฏิบัติงาน

- ASM-01 โควตาต่อช่วงเวลามีแหล่งข้อมูลที่เชื่อถือได้

- ASM-02 อนุญาตให้แก้ไขตารางได้ก่อนถึงเวลาเริ่มปฏิบัติงานเท่านั้น และห้ามแก้ไขเมื่อถึงเวลาเริ่มปฏิบัติงานแล้ว

- ASM-03 โควตาของช่วงเวลาถือว่าใช้ได้เมื่อมีค่าคงเหลือมากกว่า 0 และข้อความปฏิเสธเมื่อเต็มคือ “โควตาเต็ม”

- ASM-04 การตรวจตารางซ้ำซ้อนพิจารณาเฉพาะ Lab Boy คนเดียวกันและช่วงเวลาที่เกี่ยวข้อง

- ASM-05 ช่วงเวลาถือว่าซ้อนกันเมื่อช่วงเวลาใหม่ทับกับช่วงเวลาเดิมแม้เพียงบางส่วน

- ASM-06 การตรวจสอบและตัดโควตาเมื่อมีการบันทึกพร้อมกันใช้ Atomic Transaction

- ASM-07 เป้าหมายประสิทธิภาพของการตรวจสอบโควตาและตารางซ้ำซ้อนคือไม่เกิน 2 วินาทีใน 95% ของคำขอภายใต้การใช้งานปกติ

### UC-10 ตรวจสอบเอกสารและอนุมัติ

- ASM-01 ประเภทและรายการเอกสารที่ต้องตรวจสอบถูกกำหนดไว้ในประกาศรับสมัครหรือรายการเอกสารที่ระบุไว้ล่วงหน้า -\> Assumption: ยังต้องยืนยันกับผู้รับผิดชอบ

- ASM-02 ผู้มีสิทธิ์เข้าดูและตรวจเอกสารคือผู้ที่เกี่ยวข้องกับกระบวนการรับสมัคร เช่น อาจารย์ผู้รับผิดชอบหรือเจ้าหน้าที่ที่ได้รับมอบหมาย -\> Assumption: ยังต้องยืนยันกับผู้รับผิดชอบ

- ASM-03 เมื่อผู้สมัครส่งเอกสารใหม่หรือแก้ไขเอกสาร ระบบอาจตรวจซ้ำเฉพาะรายการที่แก้ไขเท่านั้น -\> Assumption: ยังต้องยืนยันกับผู้รับผิดชอบ

- ASM-04 ประวัติการตรวจสอบควรมีข้อมูลอย่างน้อย เช่น ผู้ตรวจ, วันที่เวลา, ผลการตรวจ, เหตุผล, สถานะเอกสาร และเวอร์ชันเอกสาร -\> Assumption: ยังต้องยืนยันกับผู้รับผิดชอบ

- ASM-05 ระบบอาจต้องจัดการเวอร์ชันเอกสารเพื่อระบุเวอร์ชันล่าสุดและเวอร์ชันที่ถูกตรวจสอบล่าสุด -\> Assumption: ยังต้องยืนยันกับผู้รับผิดชอบ

### UC-11 ประเมินการปฏิบัติงาน

### UC-12 ส่งผลการปฏิบัติงาน

- ASM-01 ขั้นตอนส่งผลถือเป็นจุดสิ้นสุดการแก้ไขตามปกติ

### UC-13 ตรวจสอบสถานะผู้ปฏิบัติงาน

- ASM-01 สถานะมาตรฐานถูกกำหนดร่วมกันทุกฝ่าย

- ASM-02 การเปลี่ยนสถานะเป็นอัตโนมัติเมื่อถึงวันเริ่มงานหรือสิ้นสุดงาน และเปลี่ยนด้วยเจ้าหน้าที่เมื่อมีการยกเลิก/พ้นสภาพ

### UC-14 ตรวจสอบเอกสารนักศึกษา

- ASM-01 รายการเอกสารบังคับที่ต้องตรวจสอบถูกกำหนดไว้ในประกาศรับสมัครแต่ละฉบับ และเป็นแหล่งข้อมูลหลัก (Single Source of Truth)

- ASM-02 นักศึกษาเห็นเฉพาะใบสมัคร ผลการตรวจ และส่งเอกสารแก้ไขของตนเอง, เจ้าหน้าที่ภาควิชาเห็นและตรวจสอบได้เฉพาะใบสมัครที่ยื่นเข้าภาควิชาตนเอง, อาจารย์ผู้สอนเห็นเฉพาะรายวิชาที่ตนเองรับผิดชอบ, และผู้ดูแลระบบเห็นใบสมัครทุกภาควิชา

- ASM-03 สถานะการตรวจสอบมี 3 ระดับมาตรฐาน ได้แก่ ผ่าน, ไม่ผ่าน, ส่งกลับเพื่อแก้ไข

- ASM-04 การแจ้งเตือนกลับไปยังผู้สมัครใช้ระบบแจ้งเตือนภายในแอปเป็นหลัก และส่งอีเมลแจ้งเตือนอัตโนมัติพร้อมลิงก์สำหรับแก้ไขเอกสาร

- ASM-Q1-01 เอกสารที่มีข้อมูลตรงกับฐานข้อมูลระบบเดิม (เช่น รหัสนักศึกษา, ประวัติการเรียน) ให้ใช้การตรวจสอบอัตโนมัติ (Auto-validation)

- ASM-Q1-02 เอกสารที่เป็นไฟล์แนบหรือต้องพิจารณาเชิงเนื้อหา (เช่น สำเนาบัตร, Transcript) ให้ตรวจสอบด้วยเจ้าหน้าที่ (Manual Review)

- ASM-Q2-01 นักศึกษามีระยะเวลาแก้ไขและส่งเอกสารใหม่ภายใน 7 วัน นับจากวันที่ได้รับแจ้งเตือน หากเกินกำหนดระบบจะเปลี่ยนสถานะใบสมัครเป็นหมดสิทธิ์อัตโนมัติ

### UC-15 จัดทำประกาศรับสมัคร

- ASM-01 รูปแบบประกาศมี template ที่กำหนดไว้ให้ใช้เป็นแหล่งข้อมูลหลัก

- ASM-02 สถานะประกาศมี 4 ระดับมาตรฐาน ได้แก่ Draft, Published, Expired, Archived

- ASM-03 เจ้าหน้าที่ภาควิชาและ Admin มีสิทธิ์เปลี่ยนสถานะจาก Draft เป็น Published ได้ทันที โดยไม่ต้องผ่านผู้อนุมัติกลาง

- ASM-04 นักศึกษาจะมองเห็นเฉพาะประกาศที่มีสถานะ Published เท่านั้น

### UC-16 ติดตามและตรวจสอบการจ่ายเงิน

- ASM-01 ระบบการเงินเป็นแหล่งข้อมูลสถานะการจ่ายเงิน; ปัจจุบัน Backend ยังไม่มี API เชื่อมต่อ จึงใช้ Mock Finance Data ที่ระบุแยกชัดเจนได้เฉพาะพัฒนา/ทดสอบ และยังไม่ถือว่าเชื่อมต่อหรือได้รับข้อมูลจริงจากระบบการเงิน

### UC-18 อนุมัติสิทธิ์การเข้าใช้งาน

- ASM-01 มี role matrix ที่กำหนดไว้

- ASM-02 การเปลี่ยนแปลงสิทธิ์หมายถึงการแก้ไขข้อมูลผู้ใช้เมื่อมีข้อมูลผิดพลาด เช่น นักศึกษาเปลี่ยนเป็นอาจารย์ หรือบทบาท/สิทธิ์กำหนดผิด โดย Admin หรือผู้ดูแลระบบสามารถแก้ไขได้ทันที โดยไม่ต้องมีการอนุมัติใหม่

### UC-19 ตรวจสอบวันและเวลาปฏิบัติงาน

- ASM-01 ระบบปฏิทินการศึกษามี API หรือแหล่งข้อมูลที่ระบบสามารถเรียกใช้ได้และเปิดให้ใช้งาน

- ASM-02 วันหยุดหรือช่วงเวลาที่ไม่อนุญาตหมายถึงช่วงที่สถาบันกำหนดไว้ในปฏิทินการศึกษา เช่น วันหยุดนักศึกษา วันหยุดราชการ ช่วงปิดภาคหรือช่วงสอบที่ห้ามจัดตาราง

### UC-20 ส่งคำขอแจ้งเตือน

- ASM-01 ระบบแจ้งเตือนรองรับ API หรือ queue แบบ asynchronous

- ASM-02 หากส่งคำขอแจ้งเตือนไม่สำเร็จ ระบบจะ retry สูงสุด 3 ครั้ง โดยแต่ละรอบมีระยะห่าง 1, 2, 4 วินาทีตามลำดับ เพื่อป้องกันการส่งคำขอเร็วเกินไป

- ASM-03 เหตุการณ์ที่ถือว่า “ต้องแจ้งเตือน” คือเหตุการณ์ที่เปลี่ยนแปลงสถานะหรือต้องให้ผู้ใช้ทราบและดำเนินการต่อ เช่น การสมัคร การอนุมัติ การปฏิเสธ การแจ้งผล หรือการเปลี่ยนแปลงตารางงาน และผู้รับคือผู้ที่เกี่ยวข้องกับเหตุการณ์นั้นโดยตรงและมีสิทธิ์รับทราบข้อมูล

### UC-21 ตรวจสอบการจ่ายเงิน

- ASM-01 ระบบการเงินมี reference ที่ใช้เชื่อมรายการภายใน LAB BOY กับรายการชำระเงิน

- ASM-02 การเรียกข้อมูลหรือ callback จากระบบการเงินอาจส่งข้อมูลซ้ำได้ จึงต้องมีการป้องกันด้วย idempotent logic

- ASM-03 สถานะจากระบบการเงินจะมีค่าที่แตกต่างจากสถานะภายใน LAB BOY และต้องมีการ map ที่ชัดเจน เช่น paid, pending, failed, cancelled, refunded ไปเป็นสถานะภายในที่เหมาะสม

- ASM-04 หากระบบการเงินส่ง callback ซ้ำหรือส่งข้อมูลที่มี timestamp น้อยกว่า/เก่ากว่าข้อมูลล่าสุด ระบบจะไม่ให้ข้อมูลเก่าทับข้อมูลใหม่ และจะพิจารณาเป็น duplicate หรือ stale event

- ASM-05 หาก reference หรือ amount ไม่ตรงกับรายการที่มีอยู่ ระบบจะถือว่าเป็นข้อมูลไม่สอดคล้องและปฏิเสธการอัปเดตโดยไม่แก้ไขสถานะเดิม และต้องบันทึกเหตุผล mismatch ใน audit log

### UC-22 แจ้งเตือนผู้ใช้งาน

- ASM-01 ระบบแจ้งเตือนรองรับ notification ภายในระบบเท่านั้น

- ASM-02 ช่องทางที่ใช้ส่งต้องเป็นช่องทางที่ผู้ใช้เปิดใช้งานและมีข้อมูลติดต่อที่ถูกต้องตามนโยบายความปลอดภัย

- ASM-03 หากผู้ใช้ไม่มีช่องทางที่พร้อมใช้งาน ระบบจะไม่ส่งข้อความและบันทึกสถานะ failed/queued พร้อมเหตุผล

### 2.5.2 สิ่งที่ต้องพึ่งพา (Dependencies)

- SSO ของสถาบันต้องส่งบทบาทของผู้ใช้ (UC-04 ASM-01, ASM-02)

- ระบบทะเบียนต้องตอบสถานะนักศึกษา (UC-05) หากล่ม ห้ามสร้างผลผ่านอัตโนมัติ (NFR-REL-01)

- ระบบการเงินต้องให้ reference สถานะ และเวลา (UC-21); mapping ของสถานะต้องยืนยันกับฝ่ายการเงิน (UC-21 Q-01)

- ปฏิทินการศึกษาที่ทราบความสดใหม่ (UC-19 NFR-REL-01)

- ระบบแจ้งเตือน (UC-20, UC-22) และ role matrix ที่กำหนดไว้ (UC-18 ASM-01)

## 3.2 External Interfaces

spec ไม่กำหนดรหัส IF- สำหรับระบบ Lab Boy ตารางนี้จึงสรุปจากข้อความใน FR/NFR/Constraints โดยไม่ตั้ง ID ใหม่

### 3.2.1 ส่วนติดต่อผู้ใช้

- แสดงสถานะ เหตุผลที่ส่งกลับ/ไม่อนุมัติ และรายการที่ต้องแก้ ให้อ่านเข้าใจง่าย (UC-03 NFR-USE-01)

- เมื่อไม่พบข้อมูลหรือข้อมูลไม่ครบในการตรวจสถานะนักศึกษา แสดงข้อผิดพลาด 404 พร้อมปุ่มรีเฟรช (UC-05 NFR-UX-01)

- ค้นหา/กรองไม่พบข้อมูล แสดงข้อความ "ไม่พบข้อมูลผู้ปฏิบัติงานตามเงื่อนไขที่ระบุ" (UC-13 FR-WKS-02)

- หน้าตรวจเอกสารแสดง checklist ของเอกสารบังคับ (UC-14 FR-OFC-01) และการแสดงผลต้องชัดเจนใช้งานง่าย (NFR-UX-01)

- แจ้งโควตาเต็มเมื่อบันทึกตารางไม่ได้ (UC-09 FR-SCH-02)

- รูปแบบหน้าจอ/ภาษา/การเข้าถึง (accessibility) ที่เฉพาะเจาะจง: spec ไม่ระบุ

### 3.2.2 ฮาร์ดแวร์

spec ไม่ระบุอินเทอร์เฟซฮาร์ดแวร์

### 3.2.3 ซอฟต์แวร์ / ระบบภายนอก

| **ระบบ**     | **UC**       | **ทิศทาง/ข้อมูล**                        | **เงื่อนไขที่ spec กำหนด**                                                                   |
|--------------|--------------|---------------------------------------|------------------------------------------------------------------------------------------|
| SSO ของสถาบัน | UC-04        | รับผลยืนยันตัวตนและบทบาท                  | อนุญาตเฉพาะรหัสนักศึกษา/บุคลากรหรืออีเมลมหาวิทยาลัย; ไม่ใช้ MFA (ASM-03, ขัดกับ Q-01 ดูข้อ E)           |
| ระบบทะเบียน   | UC-05, UC-01 | ส่งรหัสนักศึกษา+ชื่อ รับสถานะ                | เฉพาะสถานะ “ปกติ” ผ่าน; ตรวจไม่ได้ = ไม่ผ่าน; ล่มห้ามผ่านอัตโนมัติ; UC-01 FR-LB-09 ใช้สถานะ รอตรวจสอบ |
| ระบบการเงิน   | UC-21, UC-16 | รับสถานะการจ่ายเงินและเวลา ตาม reference | อัปเดตเฉพาะ reference ที่ตรง; idempotent; เชื่อมต่อแบบเข้ารหัสและยืนยันตัวตนตามนโยบาย               |
| ปฏิทินการศึกษา  | UC-19        | รับวัน-เวลาจาก UC-09 ตอบผ่าน/ไม่ผ่าน       | ตอบเป็น JSON มี status, reason, calendarVersion; ปฏิทินไม่พร้อม/ล้าสมัย = ไม่ผ่าน; ระดับวันเต็ม       |
| ระบบแจ้งเตือน  | UC-20, UC-22 | ส่งคำขอแจ้งเตือนแบบ asynchronous         | ช่องทาง: notification ในระบบเท่านั้น (UC-22 Q-01) ส่วน UC-14 ระบุอีเมลเสริมพร้อมลิงก์แก้ไข           |

### 3.2.4 การสื่อสาร

- ข้อมูลการสมัครส่งผ่านช่องทางที่เข้ารหัส (UC-01 NFR-SEC-01); การแลกเปลี่ยนกับระบบทะเบียนเข้ารหัส (UC-05 NFR-SEC-01)

- การส่งคำขอแจ้งเตือนเป็น asynchronous ธุรกรรมหลักไม่รอผล (UC-20 FR-NOT-02, NFR-PERF-01)

- โปรโตคอล/เวอร์ชัน TLS และรูปแบบ API: spec ไม่ระบุ ทีมเลือกเอง

## 3.4 Domain Requirements และข้อกำหนดตามกฎหมาย

spec ของ UC-01 ถึง UC-22 **ไม่มีรหัส DOM- และไม่ระบุกฎหมายหรือข้อบังคับเฉพาะ** สิ่งที่เกี่ยวข้องและพบใน spec มีดังนี้ ส่วนที่เกินนี้ต้องให้ทีมตัดสิน (ไม่เดาเอง)

- กฎทางธุรกิจของสถานะนักศึกษา: เฉพาะสถานะ “ปกติ” ผ่าน (UC-05 FR-REG-02)

- การคัดเลือก: ผลเป็น “ผ่าน/ไม่ผ่าน” โดยอาจารย์เจ้าของวิชา และไม่จำกัดจำนวนผู้ผ่านตามจำนวนที่รับ (UC-08 FR-SEL-01, FR-SEL-02)

- ตารางปฏิบัติงานต้องไม่ทับวันหยุด/ช่วงห้ามปฏิบัติงานของปฏิทินการศึกษา (UC-19 FR-CAL-03)

- ข้อมูลที่ขัดต่อกฎหมายหรือนโยบายของระบบต้องถูกตรวจก่อนบันทึก (UC-17 FR-ADM-02) แต่ spec ไม่ระบุว่ากฎหมายฉบับใด

- การเก็บบันทึกการเข้าสู่ระบบอย่างน้อย 1 ปี (UC-04 NFR-AUD-02) · ข้อมูลอ่อนไหวในการแจ้งเตือนต้องไม่เกินจำเป็น (UC-22 NFR-SEC-01) · ข้อมูลผู้สมัครที่อาจารย์เห็นได้ต้องยืนยันตามนโยบายข้อมูล (UC-07 Q-01)

- **รอทีมตัดสิน:** ต้องมีข้อกำหนดด้านข้อมูลส่วนบุคคลหรือระเบียบสถาบันเพิ่มหรือไม่ และระยะเวลาเก็บข้อมูลของ UC อื่นนอกจาก UC-04 (ดูข้อ E)
