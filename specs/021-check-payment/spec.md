# Feature: ตรวจสอบการจ่ายเงิน
Spec ID: SPEC-21-21- | Source: Use Case Diagram UC-21 | Use case: UC-21
Owner: ทีม A | Status: Draft v1 | Updated: 2569-09-19

## Goal
ระบบต้องตรวจสอบสถานะการจ่ายเงินที่ได้รับจากระบบการเงินสำหรับรายการที่มี reference เฉพาะเจาะจง และนำผลการตรวจสอบมาอัปเดตสถานะภายในระบบ LAB BOY ให้สอดคล้องกัน โดยมีการป้องกันข้อมูลซ้ำและข้อมูลที่ไม่ตรงรายการ

## Scope
### In scope
- ระบุหรือค้นหารายการจ่ายเงินด้วย reference ที่เกี่ยวข้อง
- รับสถานะการจ่ายเงินและข้อมูลเวลา/metadata ที่เกี่ยวข้องจากระบบการเงิน
- ตรวจสอบความถูกต้องของ reference และสถานะที่ได้รับ
- บันทึกหรืออัปเดตสถานะการจ่ายเงินภายในระบบ LAB BOY
- แมปสถานะจากระบบการเงินให้เป็นสถานะภายในที่ใช้ใน LAB BOY
### Out of scope
- การจัดการกระบวนการชำระเงินเองในระบบการเงิน (UC-16)
- การติดตามและตรวจสอบอย่างต่อเนื่องของการชำระเงินในระดับธุรกิจ (UC-16)
- การตัดสินใจคืนเงินหรือยกเลิกการชำระเงิน

## Constraints
- ระบบการเงินเป็นแหล่งข้อมูลที่เชื่อถือได้สำหรับสถานะการจ่ายเงิน
- reference ต้องเป็นคีย์ที่ใช้เชื่อมรายการภายใน LAB BOY กับรายการในระบบการเงิน
- ระบบต้องปฏิเสธการอัปเดตเมื่อ reference หรือข้อมูลสถานะไม่ตรงกับรายการที่มีอยู่
- การอัปเดตสถานะต้องเป็น idempotent และไม่สร้างรายการซ้ำ
- การเชื่อมต่อกับระบบการเงินต้องใช้การส่งข้อมูลที่เข้ารหัส

## Requirements
- FR-FIN-01 ระบบต้องค้นหาหรือระบุตัวตนรายการจ่ายเงินด้วย reference ที่ได้รับจากระบบการเงินหรือจากข้อมูลภายในระบบ LAB BOY    <- UC-21 requirement 1
- FR-FIN-02 ระบบต้องรับสถานะการจ่ายเงินและข้อมูลเวลาที่เกี่ยวข้อง เช่น เวลาการประมวลผลหรือเวลาที่รายงานสถานะ เพื่อใช้ในการอัปเดตและตรวจสอบความทันสมัย    <- UC-21 requirement 2
- FR-FIN-03 ระบบต้องอัปเดตสถานะของรายการที่ตรง reference เท่านั้น และต้องไม่สร้างรายการซ้ำเมื่อได้รับข้อมูลซ้ำหรือข้อมูลที่มีอยู่แล้ว    <- UC-21 requirement 3
- FR-FIN-04 หาก reference ไม่ตรง หรือข้อมูลสถานะไม่สอดคล้องกับรายการที่มีอยู่ ระบบต้องปฏิเสธการอัปเดตและบันทึกเหตุผลการปฏิเสธเพื่อการตรวจสอบ    <- UC-21 requirement 4

## Quality Requirements
- NFR-REL-01 การอัปเดตสถานะต้อง idempotent และต้องไม่สร้างข้อมูลซ้ำ
- NFR-SEC-01 การเชื่อมต่อระบบการเงินต้องเข้ารหัสและใช้การยืนยันตัวตนตามนโยบายความปลอดภัย

## Acceptance Criteria
- [ ] AC-FIN-01 (FR-FIN-03)
      Given มีรายการจ่ายเงินที่มี reference ที่ถูกต้องอยู่แล้ว
            When  ระบบได้รับข้อมูลการจ่ายเงินซ้ำหรือ callback ซ้ำ
            Then  ระบบไม่สร้างรายการจ่ายเงินใหม่และสถานะที่มีอยู่ยังคงสอดคล้องกับข้อมูลล่าสุด
- [ ] AC-FIN-02 (FR-FIN-02, FR-FIN-03)
      Given ระบบการเงินตอบกลับสถานะ paid พร้อม reference ที่ตรงกับรายการที่มีอยู่
            When  ระบบประมวลผลข้อมูลดังกล่าว
            Then  สถานะภายในเปลี่ยนเป็น paid ตาม mapping ที่กำหนด
- [ ] AC-FIN-03 (FR-FIN-04)
      Given ระบบการเงินตอบกลับสถานะสำหรับ reference ที่ไม่ตรงหรือข้อมูลไม่สอดคล้อง
            When  ระบบประมวลผลข้อมูลดังกล่าว
            Then  ระบบปฏิเสธการอัปเดต และไม่แก้ไขสถานะเดิมของรายการที่มีอยู่

## Assumptions & Open Questions
- ASM-01 ระบบการเงินมี reference ที่ใช้เชื่อมรายการภายใน LAB BOY กับรายการชำระเงิน
- ASM-02 การเรียกข้อมูลหรือ callback จากระบบการเงินอาจส่งข้อมูลซ้ำได้ จึงต้องมีการป้องกันด้วย idempotent logic
- ASM-03 สถานะจากระบบการเงินจะมีค่าที่แตกต่างจากสถานะภายใน LAB BOY และต้องมีการ map ที่ชัดเจน เช่น paid, pending, failed, cancelled, refunded ไปเป็นสถานะภายในที่เหมาะสม
- ASM-04 หากระบบการเงินส่ง callback ซ้ำหรือส่งข้อมูลที่มี timestamp น้อยกว่า/เก่ากว่าข้อมูลล่าสุด ระบบจะไม่ให้ข้อมูลเก่าทับข้อมูลใหม่ และจะพิจารณาเป็น duplicate หรือ stale event
- ASM-05 หาก reference หรือ amount ไม่ตรงกับรายการที่มีอยู่ ระบบจะถือว่าเป็นข้อมูลไม่สอดคล้องและปฏิเสธการอัปเดตโดยไม่แก้ไขสถานะเดิม และต้องบันทึกเหตุผล mismatch ใน audit log
- Q-01 สถานะจากระบบการเงินมีค่าอะไรบ้างที่ต้อง map ไปเป็นสถานะภายใน LAB BOY อย่างไร? -> ต้องยืนยัน mapping กับฝ่ายการเงิน
- Q-02 ระบบการเงินมี timestamp, sequence number, หรือข้อมูลอื่นที่ใช้ตรวจสอบว่า callback/response เป็นข้อมูลใหม่หรือข้อมูลเก่า? -> ต้องยืนยันกับฝ่ายการเงิน
- Q-03 เมื่อ reference ไม่ตรงหรือ amount ไม่ตรง ควรบันทึกข้อมูล mismatch อย่างไรให้เพียงพอสำหรับ audit และ incident review? -> ต้องกำหนดเพิ่มเติม
