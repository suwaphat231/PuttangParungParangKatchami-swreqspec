# Plan: ตรวจสอบการจ่ายเงิน (v2)

## วัตถุประสงค์
ปรับปรุงเอกสารข้อกำหนดความต้องการสำหรับฟีเจอร์ตรวจสอบสถานะการจ่ายเงินให้มีความชัดเจน สอดคล้อง และพร้อมใช้เป็นฐานสำหรับการออกแบบและพัฒนาระบบ โดยเน้นการยืนยัน reference การป้องกันข้อมูลซ้ำ การตรวจสอบความไม่สอดคล้อง และการแมปสถานะระหว่างระบบการเงินกับ LAB BOY

## ขอบเขตงาน
### In scope
- ระบุหรือค้นหารายการจ่ายเงินด้วย reference ที่ตรงกับข้อมูลจากระบบการเงิน
- รับสถานะการจ่ายเงินและข้อมูลเวลา/metadata ที่เกี่ยวข้อง
- ตรวจสอบความถูกต้องของ reference และ payload ที่เข้ามา
- ป้องกันข้อมูลซ้ำและการอัปเดตที่ซ้ำซ้อน
- อัปเดตสถานะภายในระบบ LAB BOY ตาม mapping ที่กำหนด
- บันทึกเหตุผลปฏิเสธเมื่อข้อมูลไม่สอดคล้องหรือ reference ไม่ตรง

### Out of scope
- การจัดการกระบวนการชำระเงินเองในระบบการเงิน
- การติดตามและตรวจสอบการจ่ายเงินในระดับธุรกิจแบบครอบคลุม
- การตัดสินใจคืนเงินหรือยกเลิกการชำระเงิน
- การส่งข้อความหรือการแจ้งเตือนให้ผู้ใช้งาน

## แผนการทำงาน
### 1. ปรับความชัดเจนของ requirement
- กำหนดให้ reference เป็นคีย์หลักสำหรับการเชื่อมรายการระหว่าง LAB BOY กับระบบการเงิน
- กำหนดให้การอัปเดตต้องตรวจสอบว่ารายการตรงกันก่อนบันทึกหรือ update
- ระบุว่าระบบต้องปฏิเสธการอัปเดตเมื่อข้อมูลไม่สอดคล้องหรือ reference ผิด

### 2. ปรับแนวทางการป้องกันข้อมูลซ้ำ
- กำหนดให้การประมวลผลสถานะจากระบบการเงินเป็น idempotent
- ระบุว่าข้อมูลซ้ำหรือ callback ซ้ำต้องไม่สร้างรายการใหม่หรือเปลี่ยนสถานะผิดพลาด
- กำหนดให้มีการตรวจสอบ duplicate ก่อนบันทึก

### 3. ปรับแนวทางการแมปสถานะ
- กำหนดให้มีการ map สถานะจากระบบการเงินไปยังสถานะภายใน LAB BOY อย่างชัดเจน
- ระบุว่าค่าที่ได้รับจากระบบการเงินต้องผ่านการ validate ก่อน update
- หากสถานะไม่มี mapping หรือค่าไม่รู้จัก ให้ปฏิเสธและบันทึก event สำหรับ audit

### 4. ปรับแนวทาง mismatch handling
- ระบุว่าหาก reference ไม่ตรง หรือ amount ไม่ตรง หรือข้อมูลไม่สอดคล้อง ระบบจะไม่อัปเดตสถานะเดิม
- กำหนดให้บันทึก mismatch reason ใน audit log เพื่อใช้ตรวจสอบต่อไป
- กำหนดให้มีแนวทางสร้าง traceability เพื่อสอบย้อนกลับได้

### 5. ตรวจสอบความครบถ้วนของเอกสาร
- Requirement ต้องครอบคลุมการค้นหา reference, รับสถานะ, ป้องกัน duplicate, และ reject mismatch
- Acceptance Criteria ต้องสามารถทดสอบได้จริงและสอดคล้องกับ requirement
- Traceability ต้องเชื่อม requirement กับ AC และ NFR อย่างถูกต้อง

## กฎทางธุรกิจที่ยืนยัน
1. reference ต้องเป็น identifier ที่ใช้เชื่อมรายการระหว่าง LAB BOY และระบบการเงิน
2. การอัปเดตสถานะต้องเป็น idempotent และไม่สร้าง data duplication
3. หากข้อมูลซ้ำหรือ stale callback มาถึง ระบบจะไม่ให้ข้อมูลเก่าทับข้อมูลใหม่
4. หาก reference หรือ amount ไม่ตรง ระบบจะปฏิเสธการอัปเดตและไม่แก้ไขสถานะเดิม
5. ข้อมูล mismatch ต้องถูกบันทึกใน audit log เพื่อใช้ตรวจสอบและวิเคราะห์เหตุการณ์ต่อไป

## ขั้นตอนการพัฒนา
### Phase 1: วิเคราะห์ข้อมูลและเชื่อม reference
- ระบุโครงสร้างของ payment record และ reference mapping
- ตรวจสอบว่ารายการที่รับมามี reference ที่ตรงกับข้อมูลในระบบ LAB BOY หรือไม่

### Phase 2: Validate payload และสถานะ
- Validate mandatory fields เช่น reference, status, timestamp
- ตรวจสอบความสอดคล้องของข้อมูล เช่น amount, transaction metadata

### Phase 3: ป้องกัน duplicate และ stale update
- ตรวจสอบว่า callback/response นี้เป็นข้อมูลซ้ำหรือข้อมูลเก่าหรือไม่
- หากเป็น duplicate หรือ stale ให้ ignore หรือ reject ตาม policy

### Phase 4: อัปเดตสถานะภายในระบบ
- อัปเดตสถานะภายใน LAB BOY เมื่อ payload ถูกต้องและเป็นข้อมูลล่าสุด
- บันทึก audit trail สำหรับทุกการอัปเดตและการปฏิเสธ

### Phase 5: ทดสอบและตรวจสอบ
- ทดสอบกรณี duplicate callback
- ทดสอบกรณี reference mismatch
- ทดสอบกรณี payment status paid
- ทดสอบกรณี payload ไม่สอดคล้องและ reject ตาม policy

## ผลลัพธ์ที่คาดหวัง
- เอกสารสเปกมีความชัดเจนและสอดคล้องกับ UC-21

- มีการแมปสถานะที่ชัดเจนระหว่างระบบการเงินและ LAB BOY
- มีแนวทางการบันทึก mismatch และ audit log สำหรับตรวจสอบภายหลัง
- สามารถใช้เป็นฐานสำหรับ design และ implementation ต่อไปได้
