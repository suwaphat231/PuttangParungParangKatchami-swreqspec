# Tasks: จัดทำตารางปฏิบัติงาน (UC-09)

## ภาพรวม
- ฟีเจอร์: จัดทำตารางปฏิบัติงาน
- Use case: UC-09
- ขอบเขตที่พิจารณา: FR-SCH-01 ถึง FR-SCH-04, NFR-REL-01, NFR-PERF-01, AC-SCH-01 ถึง AC-SCH-03
- ขอบเขตที่ไม่รวม: การตรวจสอบวันและเวลาปฏิบัติงานตาม UC-19, การติดตามและตรวจสอบการจ่ายเงินตาม UC-16, การลบ/ยกเลิกตาราง, ฟังก์ชันนอกเหนือจาก UC-09

## โครงสร้างงาน

### TASK-01: กำหนดข้อมูลและกติกาธุรกิจของตารางปฏิบัติงาน
Status: Pending
Owner: Backend / Domain Logic

- วิเคราะห์และกำหนด entity/field ที่จำเป็นสำหรับตารางปฏิบัติงาน:
  - Lab Boy
  - วัน
  - เวลาเริ่มต้น
  - เวลาสิ้นสุด
  - ช่วงเวลา
  - quota คงเหลือ
  - สถานะตาราง
- ระบุกติกาธุรกิจที่ต้องบังคับ:
  - ตารางซ้อนกันเมื่อช่วงเวลาใหม่ทับกับช่วงเวลาเดิมแม้เพียงบางส่วน
  - ห้ามจัดตารางซ้อนกันสำหรับ Lab Boy คนเดียวกัน
  - อนุญาตให้แก้ไขตารางได้ก่อนถึงเวลาเริ่มปฏิบัติงานเท่านั้น และห้ามแก้ไขเมื่อถึงเวลาเริ่มปฏิบัติงานแล้ว
  - ห้ามเพิ่มตารางเมื่อถึงเวลาเริ่มปฏิบัติงานแล้ว
  - เฉพาะอาจารย์ผู้รับผิดชอบมีสิทธิ์สร้าง แก้ไข และจัดการตารางของรอบที่รับผิดชอบ
  - ตัดสินใจแนวทางการจัดการช่วงเวลาที่ระบบกำหนดไว้ล่วงหน้าเป็น source of truth
- ผลลัพธ์ที่ต้องได้:
  - แบบจำลองข้อมูลและกติกาธุรกิจของตารางปฏิบัติงานชัดเจน
  - โครงสร้างข้อมูลรองรับ quota, overlap check และเวลาที่แก้ไขได้

Traceability:
- FR-SCH-01
- FR-SCH-02
- FR-SCH-03
- NFR-REL-01

### TASK-02: จัดทำ workflow แสดงช่วงเวลาที่เปิดให้จัดตารางได้
Status: Pending
Owner: Frontend / API

- ให้ผู้ใช้เลือก Lab Boy
- แสดงวันและช่วงเวลาที่ระบบเปิดให้จัดตาราง
- แสดงข้อมูลช่วงเวลาที่สามารถจัดตารางได้จากรายการที่ระบบกำหนดไว้ล่วงหน้า
- ป้องกันการแสดงช่วงเวลาที่ไม่ได้รับอนุญาตตามสิทธิ์ของอาจารย์ผู้รับผิดชอบ

Traceability:
- FR-SCH-01
- AC-SCH-01
- AC-SCH-02

### TASK-03: ตรวจสอบ quota ก่อนบันทึก
Status: Pending
Owner: Backend / Validation Service

- ตรวจสอบว่า quota ของช่วงเวลานั้นเหลือมากกว่า 0 ก่อนบันทึก
- หาก quota = 0 ให้ปฏิเสธบันทึกพร้อมข้อความ “โควตาเต็ม”
- หาก quota เหลือ 1 ให้อนุญาตและคำนวณ quota คงเหลือหลังบันทึก
- บันทึกข้อความตอบกลับให้มีความชัดเจนสำหรับ UI / API

Traceability:
- FR-SCH-02
- AC-SCH-01

### TASK-04: ตรวจสอบตารางซ้ำซ้อนของ Lab Boy คนเดียวกันก่อนบันทึก
Status: Pending
Owner: Backend / Validation Service

- ดึงตารางเดิมของ Lab Boy ที่เกี่ยวข้องในช่วงที่มีผลต่อการบันทึก
- ตรวจสอบว่าตารางใหม่ทับกับตารางเดิมหรือไม่
- หากพบการทับซ้อน ให้ปฏิเสธการบันทึกและแสดงรายการตารางที่ขัดแย้ง
- ต้องพิจารณาเฉพาะ Lab Boy คนเดียวกันและช่วงเวลาที่เกี่ยวข้องตามข้อกำหนด

Traceability:
- FR-SCH-03
- AC-SCH-02

### TASK-05: บันทึกตารางลงฐานข้อมูลด้วย transaction ที่ปลอดภัย
Status: Pending
Owner: Backend / Data Access

- รวมการตรวจ quota, ตรวจเวลาซ้อน, บันทึกตาราง และตัด quota ใน transaction เดียว
- ใช้ concurrency control ของ persistence layer เพื่อป้องกัน race condition
- หากมี concurrent request ให้ rollback และปฏิเสธการบันทึกโดยไม่ให้เกิด partial update
- ระวังไม่ให้ quota ติดลบหรือเกินจำนวนที่กำหนด
- ถ้าสำเร็จต้อง commit แล้วคงสถานะข้อมูลไว้ด้วยความถูกต้อง

Traceability:
- NFR-REL-01
- AC-SCH-03
- FR-SCH-02
- FR-SCH-03

### TASK-07: ทดสอบ Acceptance Criteria และเกณฑ์ประสิทธิภาพ
Status: Pending
Owner: QA / Backend

ทดสอบตามกรณีต่อไปนี้:
- AC-SCH-01
  - quota เหลือ 1 แล้วจัดตาราง 1 คน ต้องบันทึกสำเร็จและ quota เหลือ 0
  - quota เป็น 0 ต้องปฏิเสธและแจ้งว่า “โควตาเต็ม”
- AC-SCH-02
  - ตารางเดิม 09:00–12:00 กับตารางใหม่ 11:00–14:00 ต้องถูกปฏิเสธ
  - ระบบต้องแสดงรายการที่ขัดแย้ง
- AC-SCH-03
  - ส่งคำขอบันทึกหลายรายการพร้อมกันตรวจว่า quota ไม่ติดลบและไม่เกินจำนวน
  - ยืนยันว่าไม่มี partial update
- NFR-PERF-01
  - วัดเวลาในการตรวจ quota และตารางซ้ำในกรณีใช้งานปกติ
  - สรุปผลว่า p95 ต้องไม่เกิน 2 วินาที
- ตรวจสอบกรณีช่วงเวลาติดกัน, วันต่างกัน, quota เต็ม, และสิทธิ์ของอาจารย์ผู้รับผิดชอบ

Traceability:
- AC-SCH-01
- AC-SCH-02
- AC-SCH-03
- NFR-PERF-01
