### T-03: ตรวจสอบ quota ก่อนบันทึก
- รองรับ: FR-SCH-02, ASM-03
- ตรวจด้วย: AC-SCH-01
- ไฟล์ที่แตะ: ไม่มีไฟล์ implementation หรือ test ที่มีอยู่จริงใน repo สำหรับงานนี้
- ต้องทำหลัง: T-01
- เสร็จเมื่อ:
  - ตรวจสอบค่า quota ของช่วงเวลานั้นก่อนบันทึก และอนุญาตให้ดำเนินการต่อเฉพาะเมื่อ quota_remaining > 0 ตาม FR-SCH-02 และ ASM-03
  - กำหนดเงื่อนไขการตรวจสอบ quota ให้ชัดเจน: quota_remaining เป็นค่าคงเหลือจาก source of truth, ไม่ควรคำนวณจากตารางที่บันทึกก่อนหน้านี้แบบผิดพลาด, และต้องมีการตรวจสอบก่อนการสร้างหรือบันทึกตารางใหม่ทุกครั้ง
  - กรณี quota_remaining > 0: ระบบยอมให้บันทึกตารางใหม่, ส่งกลับผลลัพธ์ว่า “eligible_for_booking = true” หรือ equivalent success response, และให้ UI/API ใช้ข้อมูลนี้เพื่อดำเนินการต่อไปใน workflow ของการบันทึก
  - กรณี quota_remaining = 0: ระบบต้องปฏิเสธการบันทึกทันทีด้วยข้อความที่ต้องตรงกับข้อมูลใน spec คือ “โควตาเต็ม”, และส่งผลลัพธ์กลับเป็น error response ที่ชัดเจน เช่น { status: "rejected", reason: "quota_full", message: "โควตาเต็ม" }
  - กำหนดผลลัพธ์ที่ UI/API ต้องได้รับให้สอดคล้องกับ AC-SCH-01: สำหรับช่วงที่มีโควตาเหลือ 1 แล้วจัดตาราง 1 คน ต้องบันทึกสำเร็จและ quota เหลือ 0; สำหรับช่วงที่ไม่มีโควตาเหลือ ต้องปฏิเสธและแจ้งว่า “โควตาเต็ม”
  - ระบุว่าการปฏิเสธเมื่อ quota เต็มต้องเกิดก่อนการบันทึกตารางใดๆ และไม่อนุญาตให้สร้างตารางหรือปรับ quota แบบ partial update
  - ทดสอบเฉพาะเงื่อนไข T-03 ตาม AC-SCH-01: quota เหลือ > 0 ต้องอนุญาต, quota = 0 ต้องปฏิเสธพร้อมข้อความ “โควตาเต็ม”, และผลลัพธ์ต้องสามารถใช้ต่อใน workflow ของ T-02/T-04/T-05 ได้อย่างถูกต้อง
- สถานะ: Done

### T-04: ตรวจสอบตารางซ้ำซ้อนของ Lab Boy คนเดียวกันก่อนบันทึก
- รองรับ: FR-SCH-03, ASM-04, ASM-05
- ตรวจด้วย: AC-SCH-02
- ไฟล์ที่แตะ: ไม่มีไฟล์ implementation หรือ test ที่มีอยู่จริงใน repo สำหรับงานนี้
- ต้องทำหลัง: T-01
- เสร็จเมื่อ:
  - ดึงตารางเดิมของ Lab Boy ที่เกี่ยวข้องในช่วงที่มีผลต่อการบันทึก โดยจำกัดการค้นหาให้เฉพาะ Lab Boy เดียวกันที่กำลังพิจารณา และจำกัดช่วงเวลาให้ครอบคลุมช่วงใหม่ที่พยายามบันทึก
  - ตรวจสอบลำดับการทำงานภายใน transaction ให้สอดคล้องกับ T-05: ต้องตรวจสอบ quota ก่อนเสมอ หาก quota เหลือ > 0 แล้วจึงตรวจสอบตารางซ้ำซ้อนของ Lab Boy คนเดียวกันก่อนบันทึกตาราง
  - กำหนดหลักเกณฑ์ตรวจสอบความซ้ำซ้อนให้ชัดเจน: สำหรับ Lab Boy เดียวกัน ให้พิจารณาเฉพาะตารางที่มีวันเดียวกันหรือช่วงเวลาที่เกี่ยวข้อง, ตรวจสอบว่าช่วงเวลาใหม่และช่วงเวลาเดิมมีการทับกันหรือไม่, และถือว่าซ้อนกันเมื่อช่วงเวลาใหม่ทับกับช่วงเวลาเดิมแม้เพียงบางส่วนตาม ASM-05
  - ใช้เงื่อนไขความซ้ำซ้อนแบบ interval overlap: new_start < existing_end และ new_end > existing_start; หากเงื่อนไขนี้เป็นจริงสำหรับ Lab Boy เดียวกัน ให้ถือว่ามีการทับซ้อน
  - กรณีชัดเจน เช่น ตารางเดิม 09:00–12:00 และตารางใหม่ 11:00–14:00 ต้องถูกตรวจพบเป็น overlap เพราะ 11:00 < 12:00 และ 14:00 > 09:00
  - หากพบการทับซ้อน ให้ปฏิเสธการบันทึกทันที, ส่ง error response ที่ชัดเจน, และแสดงรายการตารางที่ขัดแย้ง พร้อมข้อมูลที่จำเป็น เช่น lab_boy_id, existing_schedule_id, existing_start_time, existing_end_time, new_start_time, new_end_time
  - ผลลัพธ์ที่ UI/API ต้องได้รับต้องสอดคล้องกับ AC-SCH-02: “ระบบปฏิเสธการบันทึกและแสดงรายการที่ขัดแย้ง” และไม่อนุญาตให้บันทึกตารางใหม่จนกว่าผู้ใช้จะแก้ไขหรือเลือกช่วงเวลาอื่น
  - ความทับซ้อนดังกล่าวต้องตรวจสอบภายใน Atomic Transaction เดียวกับการตรวจ quota และการบันทึกตาราง เพื่อให้ลำดับและกติกาเดียวกันกับ T-05 และสอดคล้องกับ T-01 ถึง T-03
  - ทดสอบเฉพาะเงื่อนไข T-04 ตาม AC-SCH-02: ตารางเดิม 09:00–12:00 กับตารางใหม่ 11:00–14:00 ต้องถูกปฏิเสธ, และต้องมีรายการ conflict ที่ชัดเจน

### T-05: บันทึกตารางลงฐานข้อมูลด้วย transaction ที่ปลอดภัย
- รองรับ: NFR-REL-01, FR-SCH-02, FR-SCH-03
- ตรวจด้วย: AC-SCH-03
- ไฟล์ที่แตะ: ไม่มีไฟล์ implementation หรือ test ที่มีอยู่จริงใน repo สำหรับงานนี้
- ต้องทำหลัง: T-02, T-03, T-04
- เสร็จเมื่อ:
  - กำหนดลำดับการทำงานก่อนบันทึกให้ชัดเจนและสอดคล้องกับ T-04: ตรวจสอบ quota -> ตรวจสอบตารางซ้ำซ้อนของ Lab Boy เดียวกัน -> บันทึกตาราง -> ตัด quota ภายใต้ Atomic Transaction เดียวกัน โดยต้องปฏิบัติในลำดับนี้เพื่อให้ได้ผลลัพธ์ที่สอดคล้องกับ FR-SCH-02 และ FR-SCH-03
  - กำหนดให้การตรวจสอบ quota, การตรวจสอบตารางซ้ำซ้อน, การบันทึกตาราง, และการตัด quota เป็น Atomic Transaction เดียว: หากมีข้อผิดพลาดหรือ validation ล้มเหลวในขั้นตอนใดๆ ต้อง rollback ทั้ง transaction เพื่อป้องกันสถานะที่ไม่สมบูรณ์
  - ระบุเงื่อนไข rollback อย่างชัดเจน: ห้ามเกิดกรณี “บันทึกตารางสำเร็จแต่ไม่ตัด quota” หรือ “ตัด quota แล้วแต่ไม่มีตาราง” และห้ามมี partial update ในฐานข้อมูลเมื่อมีข้อผิดพลาด
  - กำหนดการป้องกัน concurrent requests ให้สอดคล้องกับ NFR-REL-01 และ AC-SCH-03: ใช้ concurrency control ของ persistence layer เช่น row lock / transaction isolation / optimistic locking หรือ equivalent mechanism เพื่อให้คำขอที่ถูกส่งพร้อมกันไม่ทำให้ quota ติดลบหรือเกินจำนวนที่กำหนด
  - ระบุว่าเมื่อ concurrent request เกิดขึ้น ระบบต้องปฏิเสธคำขอที่เกิด conflict หรือ rollback transaction ที่ชนกัน เพื่อให้โควตาไม่ติดลบและไม่มีการจองเกินจำนวน
  - กำหนดผลลัพธ์การบันทึก: เมื่อทุกขั้นตอนผ่านและ transaction สำเร็จ ให้ส่งกลับ success response พร้อมข้อมูลตารางที่บันทึกแล้วและจำนวน quota คงเหลือปัจจุบัน; เมื่อ validation หรือ transaction ล้มเหลว ให้ส่งกลับ error response ที่ชัดเจนและไม่สร้างคำสั่งบันทึกที่มีผลบางส่วน
  - สอดคล้องกับ T-01 ถึง T-04 และ AC-SCH-01, AC-SCH-02, AC-SCH-03: quota เต็มต้องถูกปฏิเสธก่อนบันทึก, ตารางซ้ำต้องถูกปฏิเสธก่อนบันทึก, และการบันทึกพร้อมกันต้องไม่ทำให้ quota ติดลบหรือเกินจำนวนตาม NFR-REL-01
  - ทดสอบเฉพาะเงื่อนไข T-05 ตาม AC-SCH-03: concurrent booking ในช่วงเวลาเดียวกันต้องให้ผลลัพธ์ที่ปลอดภัย และ quota ต้องไม่ติดลบหรือเกินจำนวนที่กำหนด
- สถานะ: Done

  - หลัง transaction บันทึกตารางและตัด quota สำเร็จ ระบบต้องดึงข้อมูลตารางล่าสุดของ Lab Boy ที่เลือกตาม FR-SCH-04 โดยใช้ Lab Boy ID และช่วงเวลา/สัญลักษณ์ที่เกี่ยวข้องเป็นเงื่อนไขค้นหา
  - กำหนดขั้นตอนการแสดงข้อมูลให้ชัดเจน: ดึงตารางล่าสุดจากแหล่งข้อมูลที่บันทึกจริง, ตรวจว่าข้อมูลตรงกับ payload ที่เพิ่งบันทึก, และส่งกลับผลลัพธ์ทันทีหลังบันทึกสำเร็จ โดยไม่รอกระบวนการอื่นหรือการคำนวณเพิ่มเติมที่ไม่จำเป็น
  - ระบุข้อมูลที่ต้องแสดงสำหรับแต่ละตาราง: วันที่, เวลาเริ่มต้น, เวลาสิ้นสุด, Lab Boy, ช่วงเวลา/slot, สถานะของตาราง, และข้อมูลที่ใช้ในการยืนยันว่าบันทึกสำเร็จจริง
  - กำหนดกรณีที่ยังไม่มีตารางปฏิบัติงานของ Lab Boy ที่เลือก: ระบบต้องส่งกลับ empty state หรือ empty list ที่ชัดเจน และไม่แสดงข้อมูลเก่าหรือข้อมูลของ Lab Boy คนอื่น
  - กำหนดกรณีที่โหลดข้อมูลไม่สำเร็จ: ระบบต้องส่งกลับ error response ที่ชัดเจนและไม่ถือว่าบันทึกสำเร็จจนกว่าจะยืนยันว่าข้อมูลที่แสดงตรงกับข้อมูลที่จัดเก็บจริง
  - ตรวจสอบว่าข้อมูลที่แสดงตรงกับข้อมูลที่บันทึกจริง: วันที่ เวลาเริ่มต้น เวลาสิ้นสุด ช่วงเวลา และ Lab Boy ต้องตรงกับ payload ที่เพิ่งบันทึก และห้ามแสดงตารางที่ไม่เกี่ยวข้องหรือข้อมูลจาก transaction ที่ rollback แล้ว
  - สอดคล้องกับ T-01 ถึง T-05 และ Acceptance Criteria ใน spec.md: หลังบันทึกสำเร็จ ต้องแสดงตารางล่าสุดของ Lab Boy คนที่เลือก; ไม่รวมการลบหรือยกเลิกตาราง; และไม่คืน quota หรือเพิ่มฟังก์ชันใหม่ที่อยู่นอกขอบเขตของ UC-09
  - ทดสอบเฉพาะเงื่อนไข T-06: เมื่อบันทึกสำเร็จต้องมีตารางล่าสุดที่ถูกต้อง, เมื่อไม่มีข้อมูลต้องแสดง empty state, และเมื่อโหลดข้อมูลล้มเหลวต้องแจ้ง error อย่างชัดเจน
- สถานะ: Done

  - จัดทำ Test Scenario ในระดับเอกสารให้ครอบคลุม AC-SCH-01, AC-SCH-02 และ AC-SCH-03 ครบทุกกรณีที่กำหนด
  - กำหนด Test Case อย่างชัดเจนพร้อมข้อมูลทดสอบ, ขั้นตอน, ผลลัพธ์ที่คาดหวัง และ Acceptance Criteria ที่เกี่ยวข้อง ดังนี้:
    - TC-SCH-01A: quota เหลือ 1 และจัดตาราง 1 คน -> ต้องบันทึกสำเร็จและ quota เหลือ 0
    - TC-SCH-01B: quota = 0 และพยายามบันทึก -> ต้องปฏิเสธด้วยข้อความ “โควตาเต็ม”
    - TC-SCH-02A: ตารางเดิมของ Lab Boy เดียวกัน 09:00–12:00 และตารางใหม่ 11:00–14:00 -> ต้องปฏิเสธและแสดงรายการ conflict
    - TC-SCH-02B: ตารางเดิมและตารางใหม่ทับซ้อนเพียงบางส่วน เช่น 10:00–11:30 กับ 11:00–12:30 -> ต้องปฏิเสธเช่นกันตาม ASM-05
    - TC-SCH-03A: concurrent request 2 รายการในช่วงเวลาเดียวกันเมื่อ quota เหลือ 1 -> ต้องมีอย่างน้อย 1 request สำเร็จ และอีก request ต้องถูก Reject หรือ Rollback โดย quota ไม่ติดลบและไม่เกินจำนวนที่กำหนด
    - TC-SCH-03B: concurrent request เมื่อ quota = 0 -> ทุก request ต้องถูก Reject และไม่มีการบันทึกตารางหรือตัด quota แบบ partial update
    - TC-SCH-04: transaction failure simulation เช่น fail หลังบันทึกตารางหรือ fail ระหว่างตัด quota -> ต้อง Rollback ทั้งหมดและไม่เกิดสถานะ inconsistent
    - TC-SCH-05: การโหลดตารางหลังบันทึกสำเร็จ -> ต้องแสดงตารางล่าสุดของ Lab Boy ที่เลือก และข้อมูลต้องตรงกับ payload ที่บันทึกจริง
    - TC-SCH-06: empty state -> เมื่อ Lab Boy ยังไม่มีตาราง ต้องแสดง empty response ที่ชัดเจน และไม่แสดงข้อมูลผิด Lab Boy
    - TC-SCH-07: performance validation -> การตรวจ quota และซ้ำซ้อนต้องใช้เวลาไม่เกิน 2 วินาทีใน 95% ของคำขอภายใต้การใช้งานปกติ (NFR-PERF-01)
  - ระบุผลลัพธ์ที่คาดหวังสำหรับทุกกรณี: บันทึกสำเร็จ, ปฏิเสธด้วยข้อความ “โควตาเต็ม”, ปฏิเสธด้วยรายการ conflict, rollback เมื่อเกิด error, quota ไม่ติดลบและไม่เกินจำนวน, และ response ที่แสดงตารางล่าสุดตรงกับข้อมูลจริง
  - ตรวจสอบว่าไม่มีการจองเกิน quota และไม่มีตารางที่บันทึกแล้วแต่โควตาไม่ลดหรือลดผิดจำนวน
  - ระบุว่าการทดสอบนี้เป็น Test Scenarios ในระดับเอกสารก่อน โดยไม่ต้องสร้างหรือแก้ไข Source Code หรือ Automated Test ใน repo
  - ตรวจสอบความครบถ้วนของ T-01 ถึง T-06 ว่าครอบคลุม FR-SCH-01 ถึง FR-SCH-04 และ NFR-REL-01 / NFR-PERF-01 ตาม spec.md และ plan.md
