# แผนการพัฒนา UC-09: จัดทำตารางปฏิบัติงาน

## เป้าหมาย
นำสเปก v2 ของ UC-09 ไปออกแบบและพัฒนา โดยคง FR/NFR/AC ID เดิมทั้งหมด ไม่ขยาย Scope และไม่รวม UC-19 หรือ UC-16

## ข้อสรุปที่ใช้ในการพัฒนา
- ช่วงเวลาที่จัดตารางได้มาจากรายการที่ระบบกำหนดไว้ล่วงหน้า
- เฉพาะอาจารย์ผู้รับผิดชอบมีสิทธิ์สร้าง แก้ไข และจัดการตารางของรอบที่รับผิดชอบ
- หลังบันทึกสำเร็จ ระบบแสดงตารางล่าสุดของ Lab Boy ที่เลือก
- ไม่รองรับการลบหรือยกเลิกตาราง จึงไม่มี flow คืน quota
- แก้ไขตารางได้ก่อนเวลาเริ่มปฏิบัติงานเท่านั้น

## แผนงาน

### 1. ออกแบบข้อมูลและกติกาธุรกิจ
- กำหนดข้อมูล Lab Boy, วัน, เวลาเริ่มต้น, เวลาสิ้นสุด, ช่วงเวลา, quota คงเหลือ และสถานะตาราง
- ใช้ช่วงเวลาที่ระบบกำหนดไว้ล่วงหน้าเป็น source of truth
- ป้องกันตารางซ้ำของ Lab Boy คนเดียวกันในช่วงเวลาที่เกี่ยวข้อง
- ถือว่าตารางซ้อนกันเมื่อช่วงเวลาใหม่ทับกับช่วงเวลาเดิมแม้เพียงบางส่วน
- ป้องกันการแก้ไขเมื่อถึงเวลาเริ่มปฏิบัติงานแล้ว
- ยืนยันกติกาขอบเขตเวลาเพิ่มเติม เช่น ตารางเดิมสิ้นสุด 12:00 และตารางใหม่เริ่ม 12:00

### 2. ออกแบบ workflow และ service/API
- ให้ผู้ใช้เลือก Lab Boy
- แสดงวันและช่วงเวลาที่ระบบเปิดให้จัดตาราง
- ตรวจสอบ quota ก่อนบันทึก
- ตรวจสอบตารางเดิมของ Lab Boy คนเดียวกันก่อนบันทึก
- บันทึกตารางเมื่อ quota เหลือมากกว่า 0 และไม่พบเวลาซ้อน
- ปฏิเสธพร้อมข้อความ “โควตาเต็ม” เมื่อ quota เป็น 0
- ปฏิเสธพร้อมรายการตารางที่ขัดแย้งเมื่อพบเวลาซ้อน
- แสดงตารางล่าสุดของ Lab Boy ที่เลือกหลังบันทึกสำเร็จ
- ตรวจสอบสิทธิ์ให้อยู่ในขอบเขตของอาจารย์ผู้รับผิดชอบ

### 3. ทำให้การบันทึกเป็น Atomic Transaction
- รวมการตรวจ quota, ตรวจเวลาซ้อน, บันทึกตาราง และตัด quota ไว้ใน transaction เดียว
- ใช้ concurrency control ของ persistence layer เพื่อป้องกันการตัด quota เกินจำนวน
- ต้องไม่ทำให้ quota ติดลบหรือเกินจำนวนที่กำหนด
- เมื่อ transaction ชนกันต้องปฏิเสธหรือ rollback โดยไม่เกิด partial update

### 4. การทดสอบ
- ทดสอบ FR-SCH-02 และ AC-SCH-01:
  - quota เหลือ 1 แล้วจัดตาราง 1 คน ต้องบันทึกสำเร็จและเหลือ 0
  - quota เป็น 0 ต้องปฏิเสธและแจ้งว่า “โควตาเต็ม”
- ทดสอบ FR-SCH-03 และ AC-SCH-02:
  - ตารางเดิม 09:00–12:00 กับตารางใหม่ 11:00–14:00 ต้องถูกปฏิเสธ
  - ต้องแสดงรายการที่ขัดแย้ง
- ทดสอบ NFR-REL-01 และ AC-SCH-03:
  - ส่งคำขอบันทึกหลายรายการพร้อมกัน
  - ยืนยันว่า quota ไม่ติดลบและไม่เกินจำนวน
  - ยืนยันว่าไม่มีข้อมูลถูกบันทึกเพียงบางส่วน
- ทดสอบสิทธิ์ของอาจารย์ผู้รับผิดชอบ
- ทดสอบการแก้ไขก่อนและหลังเวลาเริ่มปฏิบัติงาน
- ทดสอบกรณีช่วงเวลาติดกัน, วันต่างกัน และ quota เต็ม
- วัด NFR-PERF-01: การตรวจ quota และตารางซ้ำต้องตอบสนองไม่เกิน 2 วินาทีใน 95% ของคำขอภายใต้การใช้งานปกติ

## Traceability
- FR-SCH-01: แสดงวันและช่วงเวลาที่สามารถจัดตารางได้
- FR-SCH-02: ตรวจ quota ก่อนบันทึกและปฏิเสธเมื่อ quota เต็ม
- FR-SCH-03: ตรวจและป้องกันตารางซ้ำของ Lab Boy คนเดียวกัน
- FR-SCH-04: แสดงตารางล่าสุดหลังบันทึกสำเร็จ
- NFR-REL-01: ตรวจและตัด quota ด้วย Atomic Transaction
- NFR-PERF-01: ตรวจ quota และเวลาซ้ำภายใน 2 วินาทีใน 95% ของคำขอ
- AC-SCH-01: กรณี quota เหลือและ quota เต็ม
- AC-SCH-02: กรณีช่วงเวลาซ้อน
- AC-SCH-03: กรณีบันทึกพร้อมกันหลายผู้ใช้

## ขอบเขตที่ไม่รวม
- การตรวจสอบวันและเวลาปฏิบัติงานตาม UC-19
- การติดตามและตรวจสอบการจ่ายเงินตาม UC-16
- การลบหรือยกเลิกตาราง
- การสร้างฟังก์ชันอื่นนอกเหนือจาก Scope ของ UC-09

## เกณฑ์เสร็จสิ้น
- FR-SCH-01 ถึง FR-SCH-04 และ NFR ที่เกี่ยวข้องมี implementation และ test ครบ
- AC-SCH-01 ถึง AC-SCH-03 ผ่าน
- การบันทึกพร้อมกันไม่ทำให้ quota ติดลบหรือเกินจำนวน
- ผลการวัด performance ผ่านเป้าหมาย p95 ไม่เกิน 2 วินาที
- ไม่แก้ไข `spec.md` และไม่สร้าง FR/AC ID ใหม่
