# Implementation Plan: สมัครเป็น Lab Boy

Spec: `SPEC-01-01`  
Source: UC-01  
Status: Draft  
Updated: 2569-09-19

## Objective
พัฒนากระบวนการสมัครเป็น Lab Boy สำหรับนักศึกษาที่เข้าสู่ระบบ โดยใช้ข้อมูลจากบัญชีผู้ใช้ ตรวจสอบคุณสมบัติและสถานะนักศึกษา บันทึกใบสมัครอย่างไม่ซ้ำ และรองรับการถอน/สมัครใหม่ตามเงื่อนไขของประกาศ

## Scope
- แสดงรายละเอียดประกาศ เงื่อนไข คุณสมบัติ ช่วงเวลารับสมัคร และจำนวนที่รับ
- แสดงฟอร์มจากข้อมูลบัญชีผู้ใช้โดยไม่ต้องแนบเอกสาร
- ตรวจสอบสถานะนักศึกษากับระบบทะเบียน
- สร้างใบสมัครพร้อมเลขใบสมัครและวันเวลาสมัคร
- ป้องกันการสมัครซ้ำและการรับสมัครเกินจำนวน
- ถอนใบสมัครก่อนอาจารย์ปิดรับสมัคร และสมัครใหม่ด้วยเลขใบสมัครใหม่
- ส่งใบสมัครสถานะ `รอตรวจสอบ` ให้อาจารย์เมื่อระบบทะเบียนตรวจสอบไม่ได้

## Design Decisions
- ผู้สมัครที่ผ่านคุณสมบัติต้องมีสถานะนักศึกษาปกติ
- ใช้เวลา `Asia/Bangkok` สำหรับวันเวลาสมัคร การถอน และการจัดลำดับคำขอ
- เมื่อจำนวนเต็ม ระบบรับคำขอตามเวลาที่การยืนยันสำเร็จ โดยต้องตัดจำนวนแบบ atomic
- การยืนยันซ้ำของใบสมัครเดิมต้องไม่สร้างรายการใหม่
- การถอนใบสมัครทำได้จนกว่าอาจารย์จะปิดรับสมัคร
- หลังถอน การสมัครประกาศเดิมครั้งใหม่ต้องได้เลขใบสมัครใหม่
- หากระบบทะเบียนตรวจสอบไม่ได้ ให้สร้างใบสมัคร `รอตรวจสอบ` และส่งให้อาจารย์ดำเนินการ

## Work Plan

### 1. Domain Model and Data Rules
- [ ] กำหนด entity/ตารางประกาศรับสมัครและช่วงเวลาเปิดรับ
- [ ] กำหนด entity/ตารางใบสมัคร โดยมีเลขใบสมัคร ผู้สมัคร ประกาศ สถานะ และวันเวลาสำคัญ
- [ ] กำหนดสถานะอย่างน้อย `ยืนยันแล้ว`, `รอตรวจสอบ`, `ถอนแล้ว`
- [ ] เพิ่ม unique/idempotency rule สำหรับใบสมัครที่ยังไม่ถอนของนักศึกษาต่อประกาศ
- [ ] กำหนดการเก็บเวลาเป็น timezone-aware และแสดงผลใน `Asia/Bangkok`

### 2. Application Read Flow
- [ ] ตรวจสอบ session และสิทธิ์นักศึกษาก่อนเข้าหน้าสมัคร
- [ ] แสดงรายละเอียดประกาศและเงื่อนไขตาม FR-LB-01
- [ ] ดึงข้อมูลที่ใช้สมัครจากบัญชีผู้ใช้
- [ ] ปิดการยืนยันเมื่อประกาศหมดช่วงรับสมัครหรือเต็มแล้ว

### 3. Eligibility and Submit Flow
- [ ] ตรวจสอบว่าประกาศอยู่ในช่วงเปิดรับสมัคร
- [ ] ตรวจสอบข้อมูลจากบัญชีผู้ใช้ที่จำเป็นให้ครบ
- [ ] เรียกระบบทะเบียนเพื่อตรวจสอบสถานะนักศึกษา
- [ ] อนุญาตเฉพาะสถานะนักศึกษาปกติ
- [ ] สร้างใบสมัคร `รอตรวจสอบ` เมื่อระบบทะเบียนตรวจสอบไม่ได้
- [ ] บันทึกใบสมัครและวันเวลายืนยันในธุรกรรมเดียวกัน
- [ ] ใช้ idempotency/unique constraint เพื่อป้องกันการยืนยันซ้ำ
- [ ] ใช้ atomic capacity check เพื่อไม่ให้รับเกินจำนวนและจัดลำดับผู้ยืนยันก่อน
- [ ] ไม่ทิ้งใบสมัครบางส่วนเมื่อการบันทึกล้มเหลว

### 4. Withdraw and Reapply Flow
- [ ] อนุญาตให้เจ้าของใบสมัครถอนก่อนอาจารย์ปิดรับสมัคร
- [ ] ปฏิเสธการถอนหลังอาจารย์ปิดรับสมัคร
- [ ] เมื่อถอนแล้ว ให้สมัครประกาศเดิมใหม่ได้
- [ ] การสมัครใหม่ต้องสร้างเลขใบสมัครใหม่
- [ ] แสดงสถานะและข้อความผิดพลาดที่เหมาะสมแก่ผู้สมัคร

### 5. Teacher Follow-up
- [ ] แสดงรายการใบสมัคร `รอตรวจสอบ` แก่อาจารย์ผู้รับผิดชอบประกาศ
- [ ] ให้อาจารย์ดำเนินการตรวจสอบและเปลี่ยนสถานะตาม workflow ที่กำหนด
- [ ] บันทึกผู้ดำเนินการและเวลาที่เปลี่ยนสถานะ

### 6. Security and Observability
- [ ] บังคับใช้ HTTPS/TLS สำหรับการส่งข้อมูล
- [ ] ตรวจสอบสิทธิ์ให้ผู้สมัครเข้าถึงเฉพาะใบสมัครของตนเอง
- [ ] ตรวจสอบสิทธิ์อาจารย์ให้เข้าถึงเฉพาะประกาศที่รับผิดชอบ
- [ ] บันทึกเหตุการณ์ยืนยัน ถอน และเปลี่ยนสถานะที่สำคัญ
- [ ] ไม่บันทึกข้อมูลส่วนบุคคลเกินความจำเป็นใน log

## Test Plan

### Functional Tests
- [ ] แสดงรายละเอียดประกาศและเงื่อนไขครบถ้วน (AC-LB-02)
- [ ] อนุญาตเฉพาะนักศึกษาสถานะปกติ (AC-LB-03)
- [ ] ปฏิเสธข้อมูลบัญชีไม่ครบและแสดงรายการที่ต้องแก้ (AC-LB-04)
- [ ] ยืนยันสำเร็จและบันทึกวันเวลา (AC-LB-01)
- [ ] แก้ไขข้อมูลก่อนยืนยัน (AC-LB-06)
- [ ] ถอนก่อนอาจารย์ปิดรับสมัครและปฏิเสธหลังปิด (AC-LB-07)
- [ ] สมัครใหม่หลังถอนด้วยเลขใบสมัครใหม่ (AC-LB-08)
- [ ] สร้าง `รอตรวจสอบ` เมื่อระบบทะเบียนไม่ตอบสนอง (AC-LB-09)
- [ ] ป้องกันการรับเกินจำนวนเมื่อยืนยันพร้อมกัน (AC-LB-10)

### Reliability and Security Tests
- [ ] กดยืนยันซ้ำแล้วมีใบสมัครเพียงรายการเดียว (AC-LB-11)
- [ ] การบันทึกล้มเหลวไม่เหลือใบสมัครที่ไม่สมบูรณ์ (AC-LB-05)
- [ ] ตรวจสอบการสื่อสารผ่านช่องทางเข้ารหัส (AC-LB-12)
- [ ] ทดสอบการเข้าถึงใบสมัครของผู้ใช้อื่นและประกาศที่อาจารย์ไม่มีสิทธิ์

## Dependencies
- ระบบ authentication/session
- ข้อมูลบัญชีผู้ใช้และบทบาท
- ระบบทะเบียนสำหรับตรวจสอบสถานะนักศึกษา
- ข้อมูลประกาศและจำนวนที่รับ
- กลไก transaction, unique constraint และ atomic update ของฐานข้อมูล

## Open Items
- [ ] ยืนยันชื่อสถานะและ workflow หลังอาจารย์ตรวจใบสมัคร `รอตรวจสอบ`
- [ ] ยืนยันรายการข้อมูลที่ถือว่า “จำเป็น” ในบัญชีผู้ใช้
- [ ] ยืนยันรูปแบบเลขใบสมัครและรูปแบบการแสดงวันเวลา
- [ ] กำหนดข้อความแจ้งเตือนและรหัสข้อผิดพลาดสำหรับกรณีเต็ม หมดเวลา สมัครซ้ำ และระบบทะเบียนขัดข้อง
