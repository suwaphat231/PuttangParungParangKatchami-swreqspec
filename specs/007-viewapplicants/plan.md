# แผนทางเทคนิค: ดูรายชื่อผู้สมัคร

## 1. สรุปแนวทาง

- Prototype นี้ให้อาจารย์เลือกดูรอบรับสมัครที่ตนมีสิทธิ์รับผิดชอบ
- หน้าจอจะแสดงเฉพาะรายชื่อผู้สมัครของรอบที่เลือกและอยู่ในสิทธิ์ของอาจารย์
- ใช้ข้อมูลตัวอย่างฝั่งหน้าบ้านเพื่อสาธิต AC-APP-01 โดยยังไม่เชื่อมฐานข้อมูลจริง
- การปฏิเสธรอบที่ไม่มีสิทธิ์และการค้นหา/กรองจะทำใน task ถัดไปตามลำดับใน tasks.md
- ข้อมูลส่วนบุคคลจะแสดงเท่าที่ spec ระบุได้ และจะไม่เพิ่มข้อมูลที่อยู่ใน Q-01

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สร้าง prototype หน้าจอ |
| Vite | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้รันและ build หน้าบ้านตามโครงสร้าง repository |
| JavaScript/JSX | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้ตามรูปแบบโค้ดใน `frontend/` |
| Python FastAPI | ทีมเลือกเอง ไม่ได้มาจาก spec | ยังไม่สร้าง backend ใน T-01 เพราะ AC-APP-01 ต้องการ prototype การแสดงผล |
| ข้อมูลตัวอย่างในหน่วยความจำ | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สาธิตผู้สมัครและสิทธิ์ของอาจารย์เท่านั้น |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| รอบรับสมัคร | `id`, `name`, `course`, `isManagedByTeacher` | FR-APP-01, NFR-SEC-01 |
| ผู้สมัคร | `id`, `studentId`, `name`, `roundId`, `status` | FR-APP-01, AC-APP-01 |
| สิทธิ์อาจารย์ต่อรอบ | `roundId`, `isManagedByTeacher` | FR-APP-01, NFR-SEC-01 |

ไม่มีฟิลด์เอกสารประกอบหรือข้อมูลติดต่อ เพราะ Q-01 ยังไม่ยืนยันข้อมูลที่อาจารย์มีสิทธิ์ดูได้

## 4. API / หน้าจอ

| รายการ | Input | Output | รองรับ |
|---|---|---|---|
| `ViewApplicantsPage` | รอบรับสมัครที่อาจารย์มีสิทธิ์ | ชื่อรอบ รายวิชา และตารางรายชื่อผู้สมัครของรอบนั้น | FR-APP-01, AC-APP-01 |

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| ระบบต้องแสดงข้อมูลเฉพาะในรอบ/รายวิชาที่อาจารย์มีสิทธิ์ | กรองรอบด้วย `isManagedByTeacher` ก่อนแสดงผล และให้ T-01 แสดงผู้สมัครจากรอบที่ผ่านสิทธิ์เท่านั้น | ใช้แล้ว |
| ข้อมูลส่วนบุคคลต้องถูกจำกัดตามบทบาทและนโยบายการเข้าถึงข้อมูล | โมเดล prototype แสดงเฉพาะ `studentId`, `name`, `status`; ข้อมูลที่ยังอยู่ใน Q-01 ไม่ถูกสร้าง | ใช้แล้ว |
| หากอาจารย์ไม่มีสิทธิ์ในรอบใด ระบบต้องปฏิเสธการเข้าถึงการดูข้อมูลของรอบนั้น | กำหนดเป็นงาน T-03 เพื่อทำ denial state และไม่แสดงรายละเอียด | ยังไม่ได้ใช้ เพราะเป็นขอบเขตของ T-03 |
| NFR-SEC-01 | ใช้สิทธิ์ระดับรอบเป็นเงื่อนไขก่อน render รายชื่อ และแยกงาน denial ใน T-03 | ใช้แล้ว |
| NFR-PERF-01 | กำหนดการค้นหา/กรองใน T-02; T-01 ไม่มีการวัด performance | ยังไม่ได้ใช้ เพราะเป็นขอบเขตของ T-02 |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| AC-APP-01 | `test_AC_APP_01` | Given มีผู้สมัครในรอบที่อาจารย์รับผิดชอบ, When เปิดรอบ, Then ตรวจว่าตารางแสดงเฉพาะผู้สมัครของรอบนั้น |
| AC-APP-02 | `test_AC_APP_02` | Given มีผู้สมัครหลายราย, When ค้นหาหรือกรองตามเงื่อนไข, Then ตรวจผลลัพธ์ตรงตามเงื่อนไขใน T-02 |
| AC-APP-03 | `test_AC_APP_03` | Given ไม่มีสิทธิ์ในรอบ, When พยายามเปิดรอบ, Then ตรวจว่าถูกปฏิเสธและไม่เห็นรายละเอียดใน T-03 |

## 7. ลำดับงาน

1. สร้างข้อมูลตัวอย่างรอบรับสมัครและผู้สมัครที่ผูกกับ `roundId` (FR-APP-01)
2. สร้าง `ViewApplicantsPage` ให้เลือกได้เฉพาะรอบที่ `isManagedByTeacher` เป็นจริง (FR-APP-01, NFR-SEC-01)
3. แสดงชื่อรอบ รายวิชา และรายชื่อผู้สมัครที่ `roundId` ตรงกับรอบที่เลือก (AC-APP-01)
4. เพิ่ม test `test_AC_APP_01` สำหรับการแสดงเฉพาะผู้สมัครในรอบที่มีสิทธิ์ (AC-APP-01)
5. เพิ่มการค้นหาและกรองตามเงื่อนไขที่ spec ระบุ (FR-APP-02, AC-APP-02)
6. เพิ่มสถานะปฏิเสธเมื่อเปิดรอบที่ไม่มีสิทธิ์ (FR-APP-03, AC-APP-03)
7. ทบทวนข้อมูลที่เปิดเผยได้หลัง Q-01 ได้รับคำตอบ (NFR-SEC-01, Q-01)

## 8. สิ่งที่ยังไม่ทำ

- **Q-01:** ข้อมูลใดบ้างที่อาจารย์มีสิทธิ์ดูได้จริง เช่น ชื่อ รหัสนักศึกษา เอกสารประกอบ หรือข้อมูลติดต่อ
- ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
