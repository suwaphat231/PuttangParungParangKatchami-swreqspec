### T-01: กำหนดเงื่อนไขการประเมินให้ครบก่อนส่งผล
- รองรับ: FR-RES-01, ASM-01
- ตรวจด้วย: AC-RES-01
- ไฟล์ที่แตะ: ไม่มีไฟล์ implementation หรือ test ที่มีอยู่จริงใน repo สำหรับงานนี้
- ต้องทำหลัง: -
- เสร็จเมื่อ:
  - ระบุเงื่อนไขว่าผลประเมินใดถือว่า “ครบ” ก่อนให้ส่งผล โดยอ้างอิงเฉพาะข้อความใน spec.md ว่า “ต้องประเมินครบก่อนส่ง” และ AC-RES-01 ที่ระบุว่า “Given ประเมินครบทุกคน When ยืนยันส่งผล Then ระบบอนุญาตให้ส่ง”
  - ระบุความสัมพันธ์ระหว่างค่า “ประเมินครบ” กับการยืนยันส่งผลตาม FR-RES-01: เมื่อประเมินครบทุกคนแล้ว ระบบจึงอนุญาตให้ยืนยันส่งผล; หากยังไม่ครบต้องไม่อนุญาตให้ส่ง
  - ระบุว่าการส่งผลถือเป็นจุดสิ้นสุดการแก้ไขตามปกติตาม ASM-01 โดยยึดเฉพาะข้อความที่มีใน spec.md ว่า “ขั้นตอนส่งผลถือเป็นจุดสิ้นสุดการแก้ไขตามปกติ” และไม่กำหนดกติกาใหม่หรือเงื่อนไขสิทธิ์ปลดล็อกที่ไม่ได้ระบุในสเปก
  - หาก spec.md ไม่ได้ระบุรายละเอียดแน่นอนเพิ่มเติม เช่น รายละเอียดฟิลด์/เกณฑ์ปริมาณ/ผู้ปลดล็อกหลังส่งแล้ว ให้คงเป็นประเด็นที่ต้องยืนยัน (TBD) และไม่คาดเดาหรือเพิ่มกติกาใหม่
- สถานะ: Done

### T-02: ตรวจสอบความครบถ้วนก่อนอนุญาตการส่งผล
- รองรับ: FR-RES-01
- ตรวจด้วย: AC-RES-01
- ไฟล์ที่แตะ: ไม่มีไฟล์ implementation หรือ test ที่มีอยู่จริงใน repo สำหรับงานนี้
- ต้องทำหลัง: T-01
- เสร็จเมื่อ:
  - ระบุขั้นตอนตรวจสอบว่ามีข้อมูลประเมินครบทุกคนก่อนอนุญาตให้ยืนยันส่งผล โดยอ้างอิงจาก T-01 ว่า “ประเมินครบ” หมายถึง “ประเมินครบทุกคน” และจาก FR-RES-01 กับ AC-RES-01 ว่าการยืนยันส่งผลต้องมีเงื่อนไขนี้ก่อน
  - ระบุกรณีที่ข้อมูลประเมินยังไม่ครบว่าระบบต้องปฏิเสธการส่งผล และไม่อนุญาตให้ยืนยันส่งผลตาม FR-RES-01
  - ระบุพฤติกรรมและผลลัพธ์ที่ต้องเกิดขึ้นให้สอดคล้องกับ AC-RES-01: เมื่อประเมินครบทุกคนและยืนยันส่งผล ระบบอนุญาตให้ส่ง; เมื่อข้อมูลไม่ครบ ระบบต้องไม่อนุญาตให้ส่ง
  - ใช้เฉพาะความหมายของ “ประเมินครบ” ตาม T-01 เท่านั้น ไม่กำหนดฟิลด์/จำนวน/เกณฑ์/ข้อความแจ้งเตือนเพิ่มเติมที่ไม่มีใน spec.md
  - หาก spec.md หรือ T-01 ไม่ได้ระบุรายละเอียดเพิ่มเติม เช่น ข้อความแจ้งเตือนหรือรายการข้อมูลที่ขาด ให้คงเป็นประเด็นที่ต้องยืนยัน (TBD) และไม่คาดเดาหรือเพิ่มกติกาใหม่
  - ตรวจสอบให้สอดคล้องกับ T-01 และ Constraint ใน spec.md ว่า “ต้องประเมินครบก่อนส่ง” โดยไม่ขัดแย้งกัน
- สถานะ: Done

### T-03: บันทึกผู้ส่งและเวลาการส่งผล
- รองรับ: FR-RES-02, NFR-AUD-01
- ตรวจด้วย: AC-RES-02
- ไฟล์ที่แตะ: ไม่มีไฟล์ implementation หรือ test ที่มีอยู่จริงใน repo สำหรับงานนี้
- ต้องทำหลัง: T-01
- เสร็จเมื่อ:
  - ระบุการบันทึกผู้ที่ยืนยันส่งผลตาม FR-RES-02: เมื่อมีการยืนยันส่งผลภายใต้เงื่อนไขที่ T-01 และ T-02 กำหนดว่า “ประเมินครบทุกคน” แล้ว ระบบต้องบันทึกผู้ที่ดำเนินการยืนยันส่งผล
  - ระบุการบันทึกเวลาที่ส่งผลตาม FR-RES-02 โดยอ้างอิงเฉพาะความต้องการให้มีการบันทึกเวลาในการส่งผล และไม่กำหนดรูปแบบเวลา/แหล่งเวลา/นามสกุลฟิลด์ใดเพิ่มเติมที่ไม่ได้ระบุใน spec.md
  - ระบุความสัมพันธ์ระหว่างข้อมูลผู้ส่ง เวลา และผลการประเมินที่ได้รับการยืนยันส่ง: ข้อมูลผู้ส่งและเวลาที่ส่งผลต้องเชื่อมโยงกับผลการประเมินที่ผ่านเงื่อนไขก่อนส่งผลแล้ว เพื่อให้เกิดประวัติการดำเนินการตาม NFR-AUD-01
  - ตรวจสอบความสอดคล้องกับ NFR-AUD-01 ว่าข้อมูลผู้ส่งและเวลาเป็นส่วนหนึ่งของประวัติการดำเนินการ/การบันทึกผลการส่งผลที่สามารถตรวจสอบย้อนกลับได้ตามข้อกำหนดที่มีอยู่ ไม่เพิ่มรายละเอียดการจัดเก็บ/ประวัติที่ spec.md ไม่ได้ระบุชัดเจน
  - ตรวจสอบให้สอดคล้องกับ AC-RES-02 ว่า เมื่อส่งผลสำเร็จและกลับมาดูข้อมูล สถานะเป็นส่งแล้ว โดยให้ T-03 เน้นเฉพาะการบันทึกผู้ส่งและเวลา ไม่ทำหน้าที่แทน T-04 ที่เป็นงานเปลี่ยนสถานะเป็นส่งแล้ว
  - หาก spec.md ไม่ได้ระบุรายละเอียดเพิ่มเติม เช่น รูปแบบเวลา แหล่งเวลาที่ใช้ หรือรายละเอียดการจัดเก็บข้อมูล ให้คงเป็นประเด็นที่ต้องยืนยัน (TBD) และไม่คาดเดาหรือสร้างกติกาใหม่
  - คงเงื่อนไขจาก T-01 และ T-02 ไว้ว่า ต้องประเมินครบทุกคนก่อนอนุญาตให้ส่งผล
- สถานะ: Done

### T-04: เปลี่ยนสถานะเป็น “ส่งแล้ว” ด้วย transaction ที่ปลอดภัย
- รองรับ: FR-RES-03, NFR-REL-01
- ตรวจด้วย: AC-RES-02, AC-RES-03
- ไฟล์ที่แตะ: ไม่มีไฟล์ implementation หรือ test ที่มีอยู่จริงใน repo สำหรับงานนี้
- ต้องทำหลัง: T-02, T-03
- เสร็จเมื่อ:
  - ระบุลำดับการทำงานก่อนเปลี่ยนสถานะ: ตรวจสอบว่าประเมินครบทุกคนตาม T-01/T-02 ก่อนอนุญาตให้ดำเนินการส่งผล; หลังจากนั้นบันทึกผู้ส่งและเวลา ตาม T-03; จากนั้นจึงดำเนินการเปลี่ยนสถานะเป็น “ส่งแล้ว”
  - ระบุให้การบันทึกข้อมูลการส่งผลและการเปลี่ยนสถานะเป็น “ส่งแล้ว” เป็นการทำงานที่ต้องเกิดขึ้นใน Atomic Transaction เดียวกัน ตาม NFR-REL-01 โดยไม่แยกขั้นตอนออกจากกัน
  - ระบุว่าหากกระบวนการบันทึกล้มเหลว ต้องไม่เปลี่ยนสถานะเป็น “ส่งแล้ว” ตาม AC-RES-03 และต้องรักษาค่าเดิมของสถานะให้เป็นปกติ
  - ระบุว่าหลังการส่งสำเร็จ ผลลัพธ์ต้องสอดคล้องกับ AC-RES-02: เมื่อกลับมาดูข้อมูล สถานะเป็นส่งแล้ว
  - ตรวจสอบให้ T-04 ไม่ทำงานซ้ำหรือทับ T-01, T-02 และ T-03 โดยเน้นเฉพาะขั้นตอนการเปลี่ยนสถานะหลังการยืนยันส่งผลและบันทึกข้อมูลที่เกี่ยวข้องแล้วเท่านั้น
  - หาก spec.md ไม่ได้ระบุรายละเอียดเพิ่มเติม เช่น กลไก Transaction หรือกติกาการจัดการข้อผิดพลาด ให้คงเป็นประเด็นที่ต้องยืนยัน (TBD) และไม่คาดเดาหรือเพิ่มเงื่อนไขใหม่
- สถานะ: Done

### T-05: บังคับกติกาการแก้ไขหลังส่งตามบทบาทและล๊อกผล
- รองรับ: ASM-01, Q-01
- ตรวจด้วย: -
- ไฟล์ที่แตะ: ไม่มีไฟล์ implementation หรือ test ที่มีอยู่จริงใน repo สำหรับงานนี้
- ต้องทำหลัง: T-04
- เสร็จเมื่อ:
  - ระบุว่าการส่งผลเป็นจุดสิ้นสุดการแก้ไขตามปกติ ตาม ASM-01 โดยไม่เพิ่มเงื่อนไขหรือกติกาใหม่ที่ไม่ได้ระบุใน spec.md
  - ระบุข้อจำกัดว่าหลังส่งแล้วต้องไม่แก้ไขโดยไม่มีสิทธิ์ ตาม Constraint ใน spec.md ว่า “เมื่อส่งแล้วต้องไม่แก้ไขโดยไม่มีสิทธิ์”
  - ตรวจสอบความสัมพันธ์ระหว่าง ASM-01, Constraint และ Q-01: ASM-01 กำหนดความเป็นจุดสิ้นสุดการแก้ไขตามปกติ, Constraint กำหนดการไม่แก้ไขโดยไม่มีสิทธิ์, และ Q-01 เป็นประเด็นเปิดที่ต้องยืนยันกับเจ้าหน้าที่ว่าผู้ใดสามารถปลดล็อกผลหลังส่งแล้ว
  - คง Q-01 เป็น Open Question ที่ยังต้องยืนยันกับเจ้าหน้าที่ โดยไม่ตัดสินใจแทนหรือกำหนดบทบาท/สิทธิ์ปลดล็อกเอง หาก spec.md ไม่ได้ระบุชัดเจน
  - ห้ามเพิ่มขั้นตอนอนุมัติ ระยะเวลา หรือเงื่อนไขการปลดล็อกใหม่ที่ไม่มีหลักฐานในสเปก
  - ตรวจสอบไม่ให้ T-05 ทำงานซ้ำกับ T-04 ซึ่งรับผิดชอบการเปลี่ยนสถานะเป็น “ส่งแล้ว” โดย T-05 ให้โฟกัสที่ข้อจำกัดการแก้ไขหลังส่งตามปกติและประเด็นเปิด Q-01 เท่านั้น
- สถานะ: Done

### T-06: ทดสอบ Acceptance Criteria และความต้องการเชิงคุณภาพ
- รองรับ: FR-RES-01, FR-RES-02, FR-RES-03, NFR-REL-01, NFR-AUD-01
- ตรวจด้วย: AC-RES-01, AC-RES-02, AC-RES-03
- ไฟล์ที่แตะ: ไม่มีไฟล์ implementation หรือ test ที่มีอยู่จริงใน repo สำหรับงานนี้
- ต้องทำหลัง: T-02, T-03, T-04, T-05
- เสร็จเมื่อ:
  - จัดทำ Test Scenarios เอกสารสำหรับ AC-RES-01 ถึง AC-RES-03 พร้อม Preconditions, Steps และ Expected Results
  - จัดทำ Test Scenarios สำหรับ NFR-REL-01 และ NFR-AUD-01 โดยใช้ข้อมูลที่สเปกระบุเท่านั้น และคงประเด็นที่สเปกไม่ได้ระบุไว้เป็น TBD
  - ตรวจสอบว่าทุก Scenario ครอบคลุม T-01 ถึง T-05 และไม่ขัดกัน
  - ระบุชัดเจนว่าเป็น Test Scenarios ในเอกสารเท่านั้น และไม่ได้รันทดสอบระบบจริง
  - คง Q-01 เป็น Open Question และไม่กำหนดผู้มีสิทธิ์ปลดล็อกผลเอง
- Test Scenarios:
  - TC-AC-RES-01-01: ส่งผลเมื่อประเมินครบทุกคน
    - Preconditions: มีผลประเมินที่ผ่านเงื่อนไขตาม T-01 และ T-02 ว่า “ประเมินครบทุกคน”; ผู้มีสิทธิ์ยืนยันส่งผลพร้อมใช้งาน
    - Steps: เปิดข้อมูลผลประเมิน; ตรวจสอบว่าผลประเมินครบทุกคน; ยืนยันส่งผล
    - Expected Results: ตาม AC-RES-01 ระบบอนุญาตให้ส่งผล; การยืนยันส่งผลสามารถดำเนินการต่อได้เมื่อเงื่อนไข “ประเมินครบทุกคน” เป็นจริง
  - TC-AC-RES-01-02: ส่งผลเมื่อประเมินไม่ครบ
    - Preconditions: มีผลประเมินที่ยังไม่ครบตาม T-01/T-02; ข้อมูลประเมินยังคงเป็นสภาพที่ไม่ผ่านเงื่อนไข “ประเมินครบทุกคน”
    - Steps: เปิดข้อมูลผลประเมิน; ตรวจสอบความครบถ้วนก่อนส่ง; พยายามยืนยันส่งผล
    - Expected Results: ตาม AC-RES-01 ระบบปฏิเสธการส่งผล; ไม่อนุญาตให้ยืนยันส่งผลจนกว่าเงื่อนไข “ประเมินครบทุกคน” เป็นจริง; ข้อความ/ผลลัพธ์ที่แสดงเป็นไปตามสเปกเท่านั้น และรายละเอียดข้อความแจ้งเตือนที่ไม่ระบุชัดเจนให้คงเป็น TBD
  - TC-AC-RES-02-01: ส่งผลสำเร็จและสถานะเป็นส่งแล้ว
    - Preconditions: มีผลประเมินที่ผ่านเงื่อนไขก่อนส่ง; การยืนยันส่งผลได้รับอนุญาตตาม AC-RES-01; ผู้ส่งและเวลาส่งผลมีข้อมูลที่บันทึกแล้วตาม T-03
    - Steps: ดำเนินการส่งผลสู่กระบวนการเสร็จสิ้น; กลับมาดูข้อมูลผลประเมิน
    - Expected Results: ตาม AC-RES-02 สถานะเป็น “ส่งแล้ว” เมื่อกลับมาดูข้อมูล; ผู้ส่งและเวลาที่บันทึกต้องสอดคล้องกับ FR-RES-02 และ NFR-AUD-01 โดยไม่กำหนดรายละเอียดเพิ่มเติมที่สเปกไม่ระบุ
  - TC-AC-RES-03-01: การบันทึกล้มเหลวระหว่างส่งผล
    - Preconditions: มีผลประเมินที่ผ่านเงื่อนไขก่อนส่ง; กระบวนการส่งผลเริ่มขึ้นแต่เกิดความล้มเหลวในการบันทึกตามสเปกที่ระบุใน AC-RES-03; สถานะก่อนหน้าไม่ใช่ “ส่งแล้ว”
    - Steps: เริ่มกระบวนการส่งผลตามปกติ; จำลอง/ตรวจสอบว่าการบันทึกไม่สำเร็จ; ตรวจสอบสถานะ
    - Expected Results: ตาม AC-RES-03 สถานะต้องไม่เปลี่ยนเป็น “ส่งแล้ว” เมื่อการบันทึกล้มเหลว; กลไก/วิธีจำลองความล้มเหลวเป็น TBD ตามที่ spec.md ไม่ได้ระบุ

    - Steps: เข้าดูข้อมูลผลประเมินที่ “ส่งแล้ว”; พยายามแก้ไขข้อมูลหรือยกเลิกการส่ง

  - TC-NFR-REL-01-01: ธุรกรรมส่งผลต้องเป็นการบันทึกและเปลี่ยนสถานะแบบเดียวกัน
