# Plan: แจ้งเตือนผู้ใช้งาน (v2)

## วัตถุประสงค์
ปรับปรุงเอกสารข้อกำหนดความต้องการสำหรับฟีเจอร์แจ้งเตือนผู้ใช้งานให้มีความชัดเจน สอดคล้อง และพร้อมใช้เป็นฐานสำหรับการออกแบบและพัฒนาระบบ โดยเน้นการระบุช่องทางที่รองรับ การจัดส่งข้อความตามสิทธิ์ของผู้ใช้ และการติดตามสถานะการส่งอย่างครบถ้วน

## ขอบเขตงาน
### In scope
- รับรายการแจ้งเตือนจากระบบที่ต้องส่งให้ผู้ใช้ทราบ
- ระบุผู้รับ เหตุการณ์ และข้อมูลที่จำเป็นสำหรับการจัดส่ง
- เลือกช่องทางที่ผู้ใช้งานได้เปิดใช้งานและยอมรับการติดต่อ
- ส่งข้อความผ่าน notification ภายในระบบเท่านั้น
- บันทึกสถานะการส่งเป็น sent/failed/queued พร้อมเหตุผลและเวลา
- ดำเนินการ retry ตามนโยบายเมื่อการส่งล้มเหลว

### Out of scope
- การจัดการชำระเงินหรือการยืนยันธุรกรรมภายนอก
- การส่ง SMS, LINE หรือ Email ภายนอกระบบ
- การดูสถานะการสมัครหรือกระบวนการยื่นสมัครแยกต่างหาก
- การกำหนดนโยบายความปลอดภัยด้านข้อมูลส่วนบุคคลนอกขอบเขตของฟีเจอร์นี้

## แผนการทำงาน
### 1. ปรับความชัดเจนของ requirement
- กำหนดให้แต่ละการแจ้งเตือนต้องระบุผู้รับ เหตุการณ์ และ metadata ที่จำเป็น
- ระบุว่าช่องทางส่งต้องเป็น notification ภายในระบบที่ผู้ใช้เปิดใช้งานและยอมรับการติดต่อเท่านั้น
- กำหนดให้ข้อมูลที่ส่งต้องไม่เปิดเผยข้อมูลที่เกินสิทธิ์หรืออ่อนไหวเกินจำเป็น

### 2. ปรับแนวทางการเลือกช่องทาง
- ระบุลำดับความสำคัญหรือเงื่อนไขของช่องทางการแจ้งเตือน
- ตรวจสอบว่าผู้ใช้มีช่องทางที่พร้อมใช้งานและมีข้อมูลติดต่อที่ถูกต้องหรือไม่
- ถ้าผู้ใช้ไม่มีช่องทางที่พร้อมใช้งาน ระบบต้องบันทึกสถานะ failed/queued พร้อมเหตุผล

### 3. ปรับแนวทางสถานะการส่ง
- กำหนดค่า status ที่ใช้เป็น sent, failed, queued
- ให้มีการบันทึกเหตุผลและ timestamp ของการพยายามส่งแต่ละครั้ง
- ใช้ความถูกต้องของสถานะเป็นพื้นฐานสำหรับ retry และ audit trail

### 4. ปรับความปลอดภัยและการเปิดเผยข้อมูล
- ตรวจสอบขอบเขตข้อมูลที่ใส่ในข้อความแจ้งเตือน
- ป้องกันการเปิดเผยข้อมูลส่วนบุคคลหรือข้อมูลอ่อนไหวที่ไม่จำเป็น
- กำหนดให้ข้อความแจ้งเตือนใช้ภาษาที่สั้น ชัดเจน และจำเป็นต่อการดำเนินงาน

### 5. ตรวจสอบความครบถ้วนของเอกสาร
- Requirement ต้องครอบคลุมผู้รับ เหตุการณ์ ช่องทางที่อนุญาต และสถานะการส่ง
- Acceptance Criteria ต้องทดสอบได้จริงและสอดคล้องกับ requirement
- Traceability ต้องเชื่อม requirement กับ AC และ NFR อย่างถูกต้อง

## กฎทางธุรกิจที่ยืนยัน
1. ผู้ใช้ต้องมีสิทธิ์ได้รับการแจ้งเตือนและมีข้อมูลช่องทางที่ถูกต้อง
2. ระบบต้องส่งผ่าน notification ภายในระบบเท่านั้น
3. ข้อความแจ้งเตือนต้องมีข้อมูลที่จำเป็นต่อการแจ้งสถานะหรือเหตุการณ์เท่านั้น
4. เมื่อส่งล้มเหลว ระบบต้องบันทึกสถานะ failed/queued และ retry ตามนโยบาย
5. ข้อมูลอ่อนไหวหรือข้อมูลส่วนบุคคลต้องไม่ถูกเปิดเผยเกินความจำเป็น

## ขั้นตอนการพัฒนา
### Phase 1: วิเคราะห์เหตุการณ์และผู้รับ
- ระบุเหตุการณ์ที่ต้องส่งแจ้งเตือน
- ระบุผู้รับและสิทธิ์การรับข้อมูล
- ตรวจสอบว่าผู้ใช้มีช่องทางที่ใช้งานได้หรือไม่

### Phase 2: สร้าง payload แจ้งเตือน
- สร้างข้อความที่มีผู้รับ เหตุการณ์ และ metadata ที่จำเป็น
- ตรวจสอบให้แน่ใจว่า payload ไม่เปิดเผยข้อมูลเกินสิทธิ์

### Phase 3: เลือกและส่งช่องทาง
- เลือก notification ภายในระบบที่ผู้ใช้เปิดใช้งาน
- ส่งข้อความและติดตามผล

### Phase 4: บันทึกสถานะและ retry
- บันทึก sent/failed/queued ตามผลลัพธ์
- หากส่งไม่สำเร็จ ให้ retry ตามนโยบายที่กำหนด

### Phase 5: ทดสอบและตรวจสอบ
- ทดสอบกรณีส่งสำเร็จ
- ทดสอบกรณีช่องทางไม่พร้อม
- ทดสอบกรณีข้อมูลมีความอ่อนไหวและต้องถูกลดข้อมูล
- ทดสอบสภาวะ retry และบันทึกสถานะอย่างถูกต้อง

## ผลลัพธ์ที่คาดหวัง
- เอกสารสเปกมีความชัดเจนและสอดคล้องกับ UC-22
- ระบบแจ้งเตือนผู้ใช้โดยใช้ notification ภายในระบบเท่านั้น
- การเลือกช่องทางและการส่งข้อความเป็นไปตามสิทธิ์และความยินยอมของผู้ใช้
- มีการบันทึกสถานะการส่งและการ retry ที่ตรวจสอบได้
- มีการปกป้องข้อมูลส่วนบุคคลและข้อมูลอ่อนไหวตามแนวทางความปลอดภัย

## สถานะปัจจุบัน
- Completed: ปรับ requirement ให้ระบุผู้รับ เหตุการณ์ และการเปิดเผยข้อมูลที่จำกัด
- Completed: ยืนยันช่องทางรองรับเป็น notification ภายในระบบเท่านั้น
- Completed: ปรับ acceptance criteria ให้ครอบคลุมการส่งสำเร็จ การส่งล้มเหลว และความปลอดภัยของเนื้อหา
- Completed: อัปเดตเอกสารเวอร์ชัน v2 สำหรับ folder นี้
