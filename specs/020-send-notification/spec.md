# Feature: ส่งคำขอแจ้งเตือน
Spec ID: SPEC-20-20 | Source: Use Case Diagram UC-20 | Use case: UC-20
Owner: ทีม A | Status: Draft v1 | Updated: 2569-09-19

## Goal
ระบบต้องสร้างและส่งคำขอแจ้งเตือนไปยังระบบแจ้งเตือนเมื่อเกิดเหตุการณ์ที่ต้องแจ้งข้อมูลให้ผู้ใช้งานทราบ โดยไม่ทำให้ธุรกรรมหลักต้องรอผลการส่ง

## Scope
### In scope
- ตรวจสอบเหตุการณ์ที่ต้องส่งแจ้งเตือน
- สร้าง payload หรือคำขอแจ้งเตือนที่มีข้อมูลจำเป็น
- ส่งคำขอแบบ asynchronous ไปยังระบบแจ้งเตือน
- รับและบันทึกสถานะการรับคำขอ
- บันทึกข้อความที่ส่งไม่สำเร็จเพื่อส่งซ้ำตามนโยบาย
### Out of scope
- การเลือกช่องทางส่งข้อความให้ผู้ใช้ (UC-22)
- การสร้างเนื้อหาการแจ้งเตือนแบบสมบูรณ์สำหรับผู้ใช้
- การส่งข้อความจริงต่อผู้ใช้งาน

## Constraints
- ธุรกรรมหลักต้องไม่รอผลการส่งคำขอแจ้งเตือน
- คำขอแจ้งเตือนต้องมีข้อมูลที่จำเป็นต่อการประมวลผลเท่านั้น และต้องไม่เปิดเผยข้อมูลที่เกินสิทธิ์
- ระบบต้องสามารถรองรับการส่งซ้ำเมื่อมีปัญหาการเชื่อมต่อหรือระบบปลายทางไม่พร้อม

## Requirements
- FR-NOT-01 ระบบต้องตรวจสอบว่าเหตุการณ์ที่เกิดขึ้นต้องส่งการแจ้งเตือน และสร้างคำขอแจ้งเตือนที่มีข้อมูลจำเป็น เช่น เหตุการณ์ ผู้รับ และ metadata ที่เกี่ยวข้อง    <- UC-20 requirement 1
- FR-NOT-02 ระบบต้องส่งคำขอแจ้งเตือนไปยังระบบแจ้งเตือนแบบ asynchronous โดยไม่ทำให้ธุรกรรมหลักต้องรอผลลัพธ์    <- UC-20 requirement 2
- FR-NOT-03 หากการส่งคำขอแจ้งเตือนไม่สำเร็จ ระบบต้องบันทึกรายการในคิวหรือประวัติการส่งเพื่อทำการ retry ตามนโยบาย    <- UC-20 requirement 3

## Quality Requirements
- NFR-REL-02 รายการส่งไม่สำเร็จต้องถูก retry ตามนโยบายที่กำหนด
- NFR-PERF-01 ธุรกรรมหลักต้องไม่ถูกหยุดหรือรอผลจากการส่งการแจ้งเตือน

## Acceptance Criteria
- [ ] AC-NOT-01 (FR-NOT-01, FR-NOT-02)
      Given มีเหตุการณ์ที่ต้องแจ้งเตือน
            When  ระบบสร้างและส่งคำขอแจ้งเตือน
            Then  ระบบสร้าง payload ที่มีข้อมูลที่จำเป็นและธุรกรรมหลักดำเนินต่อได้โดยไม่รอผลการส่ง
- [ ] AC-NOT-02 (FR-NOT-03)
      Given ระบบแจ้งเตือนไม่พร้อมหรือส่งคำขอไม่สำเร็จ
            When  ระบบพยายามส่งคำขอแจ้งเตือน
            Then  รายการถูกบันทึกไว้ในคิว/ประวัติการส่งเพื่อ retry ตามนโยบาย

## Assumptions & Open Questions
- ASM-01 ระบบแจ้งเตือนรองรับ API หรือ queue แบบ asynchronous
- ASM-02 หากส่งคำขอแจ้งเตือนไม่สำเร็จ ระบบจะ retry สูงสุด 3 ครั้ง โดยแต่ละรอบมีระยะห่าง 1, 2, 4 วินาทีตามลำดับ เพื่อป้องกันการส่งคำขอเร็วเกินไป
- ASM-03 เหตุการณ์ที่ถือว่า “ต้องแจ้งเตือน” คือเหตุการณ์ที่เปลี่ยนแปลงสถานะหรือต้องให้ผู้ใช้ทราบและดำเนินการต่อ เช่น การสมัคร การอนุมัติ การปฏิเสธ การแจ้งผล หรือการเปลี่ยนแปลงตารางงาน และผู้รับคือผู้ที่เกี่ยวข้องกับเหตุการณ์นั้นโดยตรงและมีสิทธิ์รับทราบข้อมูล
